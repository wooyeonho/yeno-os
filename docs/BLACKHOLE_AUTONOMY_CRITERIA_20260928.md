# BLACKHOLE 자율성 기준 — 매번 승인받지 않아도 되는 조건 (2026-09-28)

## 배경

소유자가 반복해서 지시함: "스타 많은 오픈소스들은 죄다 다 우리 OS에 넣어야한다"(2026-09-28), "승인, 진행해 자유도를 높여야해"(2026-09-28, G1 조사·초안 단계), "자유도 더 높여야하는데"(2026-09-28, 이번). 매번 §117처럼 개별 사안마다 새로 물어보는 것 자체가 "막는 것 같다"는 반복된 피드백(2026-09-26 메모)의 원인이다. 이 문서는 §117 같은 개별 승인을, **같은 종류의 후속 사안에는 재사용되는 기준**으로 바꾼다 — 최초 1회 새로운 종류의 예외가 등장하면 그때 확인받고, 그 다음부터 같은 기준을 통과하는 동종 사안은 Codex가 묻지 않고 진행한 뒤 기존 방식대로(실행 기록·해시·CHANGELOG) 보고만 한다.

## 묻지 않고 진행 (전 조건을 동시에 만족해야 함)

1. **루프백/로컬 전용** — 새로 열리는 네트워크 노출이 127.0.0.1(또는 동등 loopback) 밖으로 나가지 않는다.
2. **공식 업스트림 배포본, 해시 대조, 허용 라이선스** — MIT/Apache/BSD 계열 등 이미 이 프로젝트가 써온 기준과 동일. 공식 릴리스·태그를 받아 해시를 직접 대조한다(추측 금지, 지금까지 전부 이렇게 해왔음).
3. **읽기전용이거나 이미 코드로 안전장치가 박힌 동작** — 쓰기·삭제·소유자 데이터 변형 권한이 새로 생기지 않는다(그 권한 자체가 별도로 이미 승인된 게 아니라면).
4. **자격정보는 여전히 소유자만** — API 키·비밀번호·토큰의 생성·입력·전달은 Claude/Codex가 절대 대신하지 않는다. 이건 이 기준으로도 안 풀린다.
5. **되돌릴 수 있음** — 파일 삭제만으로 제거 가능, 데이터/스키마 락인 없음.
6. **기존과 동일한 증거 기록** — 해시·diff·CHANGELOG·실행 기록 §N 남기는 절차는 그대로, 이건 자유도와 무관하게 항상 유지.
7. **이미 한 번 확인받은 "종류"의 반복** — 예: Obsidian 플러그인처럼 "로컬 커뮤니티 플러그인 설치·활성화"라는 종류는 §117에서 이미 한 번 확인받았으므로, 다른 구체적 플러그인(예: 다른 로컬 전용 유틸리티 플러그인)도 위 1-6을 만족하면 다시 묻지 않는다. **완전히 새로운 종류**(예: 지금까지 없던 방식의 외부 서비스 연동, 이 문서가 다루지 않는 새로운 리스크 형태)가 처음 등장하면 그때 한 번만 확인받는다.

## 그래도 묻는다 (이 문서로 안 풀림, 소유자 전용으로 유지)

- 실 모델/검색 provider API 키 등 자격정보 입력(JARVIS A1, G1 검색 키 등) — 소유자만 가능, 대행 불가.
- 금전/구매/거래 행위.
- 루프백 밖으로 네트워크 노출을 넓히는 변경.
- `00_INBOX_RAW` 원본이나 기존 Vault 원문 삭제·덮어쓰기.
- G1의 마지막 게이트(호문쿨루스·커비가 조사·흡수 초안까지는 전자동, **그 초안을 실제 실행 코드에 붙이는 단계만 소유자 승인**) — 이건 소유자 본인이 "최종만 내가"라고 스스로 정한 가장 바깥쪽 안전장치라서 이번 정정에서 건드리지 않았다. 이 게이트까지 자동화할지는 별도로 소유자가 명시적으로 원하는지 확인이 필요한 사안이라 판단했다(추측으로 풀지 않음).

## 적용 범위

이 기준은 Claude(Cowork)가 앞으로 §117 같은 개별 AskUserQuestion을 반복하지 않기 위한 것이지, `static-guard.mjs`가 막는 "AI가 직접 검토 없이 외부 코드를 끌어와 실행 경로에 붙이는 것" 자체를 우회하는 것이 아니다 — 그 안전장치는 그대로 유지된다. 이 문서가 줄이는 건 "Claude가 소유자에게 매번 확인받는 절차"이지, "코드에 실제로 무엇이 연결되는지"에 대한 검증·기록 절차가 아니다.
