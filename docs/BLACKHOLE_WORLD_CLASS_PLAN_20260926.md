# BLACKHOLE 세계 최고 수준을 향한 실행 계획

작성일: 2026-09-26. 이 문서는 목표와 수락 기준이다. 현재 구현·시험의 판정은 `docs/CLAUDE_EXECUTION_STATE.md`에만 기록한다. “세계 최고”는 선언이나 화면 한 장으로 증명되지 않는다. 같은 과제를 다른 제품과 직접 비교하고, 사용자에게 돌아온 실제 결과·시간·비용·신뢰성을 반복 측정해 입증한다.

## 한 문장의 제품 약속

소유자가 휴대폰이나 PC에서 원하는 **결과**를 말하면, BLACKHOLE이 허가된 맥락을 읽고, 일을 나눠 실행하고, 독립 검증을 거쳐, 진행·결과·근거·남은 일을 한곳에 보여주며, 실패와 배운 점도 다음 요청에 쓰는 개인 AI 운영체제.

제품 전체는 BLACKHOLE, 대화와 조종의 얼굴은 JARVIS다. Kirby·Homunculus/Seven Drives·Shadow Army·Verifier/JEV는 실제 동작과 권한이 확인된 범위에서만 기능으로 소개한다. “자유의지·자유생명·자유권한”은 의식이나 무제한 권한 주장이 아니라, 소유자가 정한 목표와 경계 안에서 스스로 순서·도구·작업자를 선택하고, 중지·철회·감사를 언제든 받는 **유용한 자율성**으로 구현한다.

## 출발점과 우선순위

- 정본 비전은 `docs/BLACKHOLE_PRODUCT_VISION.md`, 세부 실행 증거는 `docs/CLAUDE_EXECUTION_STATE.md`, 아이디어 원장과 소유자 의도는 Vault `01_DRAFTS/20260926_BLACKHOLE_IDEA_LEDGER_R3_RECHECK_COMPLETE/`의 `13_OWNER_INTENT.md` 및 저장소 인계 기록을 따른다. 1,117개 아이디어는 개별 ID와 상태를 보존한다. 이 계획은 그것들을 임의로 통합하거나 전부 구현 완료로 간주하지 않는다.
- 2026-09-26 시작 근거: Android 프로젝트와 ARM64 debug APK의 정적 빌드·서명 검사는 완료됐지만, **실제 휴대폰의 QR 페어링→요청→Windows 실행→진행·결과→앱/PC 재시작 복구는 미검증**이다. ADB 연결은 0대였다. `/jarvis`는 실제 API/브라우저 경로로 실행됐으나 제품 품질·실기기 품질의 비교 우위를 입증하지 않았다.
- 현재 코어의 Shadow 동시 실행 설정 상한은 3, 합성 transport에서 두 leaf 작업 병렬 실행이 확인됐다. 실물 로컬 모델의 기존 임무는 최종 의미 검증 실패 사례가 있다. `workers/developer`는 코드 경로와 시험이 있지만 이 PC의 Docker 실물 실행·PR 운영 처리량은 확인되지 않았다.
- 따라서 **첫 번째 출시 차단 조건은 폰↔Windows 실기기 흐름**이다. 다른 축은 병행해서 보강하되, 합성 시험이나 화면 미감을 이 조건의 대체 합격으로 쓰지 않는다.

## 순서와 완료 조건

### 0. 사실과 기준 고정 — 즉시

`docs/CLAUDE_EXECUTION_STATE.md`와 현재 저장소에서 각 기능의 **코드/빌드/합성/실물/운영** 단계를 따로 표시한다. 성공·실패를 포함한 10개 소유자 과제의 입력, 허용 자료, 기대 결과, 금지 행동, 채점자, 시간·비용을 미리 고정한다. 실기기 시험에 쓸 APK와 Windows 설치물의 SHA-256·버전·출처를 기록한다. 테스트 수가 늘어난 것만 제품 성능 향상으로 부르지 않는다.

완료 증거: 재현 가능한 과제 세트와 기준선 보고서, 실제 테스트 환경 명세. 다른 사람이 같은 과제를 다시 채점할 수 있어야 한다.

### 1. 개인용 실사용 수직 흐름 — 최우선

실제 Android 휴대폰에 현재 APK를 설치한다. 휴대폰에서 QR로 안전하게 등록하고, 요청을 전송한다. Windows resident가 허가된 작업을 실제로 수행하는 동안 진행 상태가 휴대폰에 보이고, 완료·실패 결과와 산출물 근거를 휴대폰에서 연다. 앱을 강제 종료·재개하고 PC를 오프라인·재시작한 뒤 같은 요청 ID로 복구한다. 기기 폐기와 새 등록도 시험한다. 페어링 비밀은 채팅·터미널·로그에 출력하거나 사람이 옮겨 적지 않는다.

완료 증거: `P02→J01→R01/F01` 실기기 동영상/화면·서버/앱 시각·요청/작업/산출물 ID·SHA·버전, 오프라인/실패/재시작/중복 방지 결과. 실기기 없이 수행한 대체 시험은 따로 표기한다. Windows 설치와 재부팅 후 resident 자동 복귀도 실제로 확인한다. 운영 배포·데이터 삭제·실제 자격증명 교체는 이 검증에 포함하지 않는다.

### 2. 매일 쓰고 싶은 JARVIS — 1단계와 병행, 실기기 평가로 종결

한 화면에서 **말하기/입력→현재 하는 일→승인 필요→결과**가 명확히 이어져야 한다. 화면은 실제 API와 같은 권한 경계에서만 작동한다. 전체 멈춤·취소·재개·승인 대기는 숨지 않는다. 아름다움은 절제된 정보 계층, 안정된 타이포그래피·간격·동작, 한국어 가독성, 빠른 피드백으로 만든다. Seven Drives 숫자·호를 장식으로 노출하지 않는다. 400px·고대비·키보드·스크린리더·reduced motion·네트워크 실패에서 확인한다.

완료 증거: 실제 Android/Windows 화면 캡처와 5회 사용성 관찰, 핵심 과제 성공률·수정 횟수, 접근성 검사. 웹 표면은 [WCAG 2.2](https://www.w3.org/TR/wcag/) 기준으로 점검한다. “세계 1위처럼 보인다”는 내부 디자인 목표이며 객관적 시장 순위로 발표하지 않는다.

### 3. 결과까지 가는 두뇌와 손 — 수직 흐름 통과 후 확장

JARVIS가 한 요청을 목표·작업·증거에 연결하고, Homunculus가 기존 목표의 우선순위를 반영한다. Scout/Researcher의 **실제 저장 산출물**을 Builder에 전달하고, Builder 결과는 파일 해시의 결정론 검증과 내용의 독립 검증을 모두 통과해야 완료된다. 막힘에는 JEV가 근거 있는 대안을 제시하되 스스로 승인권을 만들지 않는다. 연구/제작 worker도 실행 로그·근거·산출물 SHA를 남긴다. 외부 코드 작업자는 고정 소스·허용 파일·격리 실행·시험·차이 검토를 통과한 후보만 올린다.

완료 증거: 실제 로컬 모델의 복수 임무에서 최종 의미 검증 통과, 실패 임무에서 거짓 완료 0, 재시작 후 같은 임무 이력, worker별 증거 첨부율 100%. Docker가 없는 PC에서 컨테이너 실행을 합격으로 표시하지 않는다.

### 4. 출처 있는 기억과 개선 — 성과로 검증

Kirby는 원문/부분열람/미열람과 결정·구현 상태를 보존하고, 같은 문제를 다시 받을 때 관련 자료·과거 성공/실패를 근거와 함께 회수한다. 키워드 검색, 임베딩 검색, 모델 학습을 구분한다. 능력 등급은 실행 증거로만 바뀌고, 최근 N회 실제 검증 통과율과 과제별 품질 변화는 **감지·보고**만 한다. 퇴행 때문에 자동 비활성화할지는 별도 결정이다. Vault는 `00_INBOX_RAW` 읽기 전용, 새 정리 초안만 `01_DRAFTS`, 기존 링크·분류·본문 변경은 승인 후 시행한다.

완료 증거: 재사용 전후 동일 유형 과제의 시간/품질 비교, 잘못 회수된 기억의 교정·출처 표시, 백업/복원 뒤 기억 연결 보존. 출처가 없거나 오래된 기억은 자율 실행 권한이 아니다.

### 5. 안전하게 규모를 키우기 — 품질·자원 측정 후

먼저 현재 동시 2개 실제 모델 호출의 CPU·RAM·큐 대기·완수율·비용·중단 복구를 잰다. 그 다음 단일 writer와 모델/일일 예산 제약 안에서 2→3처럼 한 단계씩 부하 시험한다. 한도 증가가 품질을 떨어뜨리면 되돌린다. 독립 작업은 격리하고 동일 프로젝트의 승격은 검증 순서로 직렬화한다. CI에는 비밀 접근·무허용 네트워크/파일쓰기·승인 우회 검사를 위반 사례 red→green으로 추가한다.

완료 증거: 동시 N개 실제 작업의 시작/끝·큐 시간·성공/실패·증거율·메모리·모델 호출·중단 응답, 같은 입력의 N-1 대비 품질/효율 비교. 소유자 승인·외부 코드의 라이선스/커밋/해시/fixture 검토는 유지한다. “15–20개”나 “월 1,000 PR”은 이 PC의 목표 수치로 복사하지 않는다.

### 6. 장기 연구: 학습·양자·사업화

딥러닝 하네스는 먼저 **기억 회수/랭킹에서 실제 개선이 필요한지** 평가 세트로 확인한다. 필요할 때만 데이터 동의·출처·학습/검증 분리·재현성·모델 등록·퇴행/삭제 절차를 만든다. 임베딩 생성이나 XP 등급은 학습으로 부르지 않는다. QPU는 게이트 회로/고전 fallback과 실제 하드웨어 제출을 구분하고, 계정·비용·문제 적합성·고전 baseline보다 나은 결과가 입증될 때 별도 실험으로 연다. 수입·브랜드 확장은 외부 사용자 문제 검증, 승인된 판매/발송, 실제 비용·재구매 근거를 본 뒤 진행한다.

완료 증거: 학습은 고정 평가 세트의 재현 가능한 개선, QPU는 provider 작업 ID/실측 counts/비용과 고전 대조, 사업은 실제 사용자·매출/반복 사용 기록. 어느 것도 개인용 기본 흐름의 완료 조건을 대체하지 않는다.

## 가로지르는 출시 게이트

- **정직한 상태:** “코드 있음 / 빌드됨 / 합성 시험 / 실기기 / 운영 중”을 UI와 기록에서 분리한다. 검증기가 `uncertain`이면 결과를 보존하되 성공으로 표시하지 않는다.
- **보안과 회복:** Android은 [OWASP MASVS](https://mas.owasp.org/MASVS/)의 저장·암호화·인증·네트워크·플랫폼·코드·프라이버시 항목에 맞춰 확인한다. AI 위험은 [NIST AI RMF](https://airc.nist.gov/)처럼 위험을 식별·측정·관리하는 반복 평가로 다룬다. 이 기준을 언급하는 것만으로 인증을 받았다는 뜻은 아니다.
- **실행 권한:** 모델, 기억, 외부 자료, JEV 판정은 명령 권한이 아니다. 승인·전체 멈춤·기기 철회·비용 상한·비밀 격리를 코드와 실물 시험 모두에서 유지한다.
- **배포:** 후보 변경→정적/관련 회귀→실제 기기/PC 수락→소유자 최종 검토 순서. 빌드 성공을 설치·실사용 성공으로 승격하지 않는다.

## 지금 바로 이어갈 한 단계

현재 진행 중인 격리 실모델 Shadow 재시험을 마치고 Builder의 실제 노트 수신·최종 의미 검증·자원 사용량을 기록한다. **제품 출시의 다음 차단 게이트는 실제 Android 기기 연결 후 1단계 실기기 수락**이며, 그 사이에는 기억·증거·UI의 재현 가능한 결함을 계속 고친다. 이 문서의 단계는 구현 허가를 새로 만들지 않으며 운영 배포·결제·대외 발송·자격 증명 변경은 기존 승인 경계를 따른다.
