# 최초 Codex Cloud 작업

이 문서는 이미 수행한 최초 구현 지시의 기록입니다. 현재 코어는 0.2.0 후보이며, 다음 작업은 `STATUS.md`와 `ANDROID_BUILD.md`를 따릅니다. 원본 0.1.1 무결성 검사를 현재 변경 코드의 통과 조건으로 사용하지 않습니다.

대상 저장소는 `wooyeonho/yeno-os`이며, 초기 소스는 이미 폴더로 등록되어 있다. ZIP 업로드나 압축 해제를 사용자에게 다시 요청하지 않는다.

```text
YENO OS 개발을 시작하라. 최종 목표는 Android APK와 Windows EXE에서
일상적으로 명령하고 확인하는 개인 OS다. 폰을 닫아도 서버에 맡긴 일이 이어져야 한다.

먼저 AGENTS.md, YENO_START_HERE.md, docs/STATUS.md와 실제 코드를 읽는다.
runtime/은 기존 0.1.1 실행 코어다. 루트 README와 기존 코드를 보존·확장한다.

Node 24에서 npm run verify:baseline과 npm test를 실행하고 결과를 남긴다.
verify:baseline은 최초 수입한 코드 검증용이다.
의도적으로 코드를 수정한 후 이전 해시와 다르다는 이유로 되돌리지 않는다.

이번 실제 구현 목표:
Tauri 2 공용 controller를 만들고, 기존 코어와 연결해
명령 접수 -> 실제 결과 -> 앱 재접속 후 같은 상태 확인 흐름을 구현한다.
기존 상대 API 주소와 sessionStorage 토큰을 그대로 포장하지 않는다.
API 연결 계약, 네이티브 인증 저장과 기기별 폐기 경로를 실제로 설계·구현하고 검증한다.

앱 구현과 독립적인 코어 보완은 이어서 수행한다.
상주 서버 배포 계정이 아직 없으면 배포 설정과 필요 항목까지 준비한다.
원격 접속·유료 모델·실기기 검증이 안 된 부분은 미검증으로 표시한다.

필요한 패키지, Rust, Android SDK/NDK가 실제 환경에 있는지 확인하고
누락된 의존성과 네트워크 조건을 구체적으로 정리해 설치·빌드 설정을 작성한다.
Android 연결을 먼저 완성하고, Windows 빌드는 독립된 후속 작업으로 준비한다.
실제 빌드했으면 APK/EXE와 검사 결과를 수집한다.
현재 환경에서 빌드하지 못하면 정확히 어떤 도구가 부족한지와
준비한 빌드 설정을 보고한다. 워크플로 작성만으로 빌드 성공이라 말하지 않는다.

기존 소스·기억을 보존하고 적용되는 Vault 규칙을 지킨다.
새 지출과 외부 공개는 이 작업만으로 허용됐다고 해석하지 않는다.
사용자에게 설정 질문을 한꺼번에 늘어놓지 말고,
구현 가능한 범위를 마친 뒤 진행을 막는 다음 항목 하나를 묻는다.

완료 보고: 수정한 코드, 실제 실행한 검사, 생성된 결과 파일,
아직 연결이 필요한 항목, 다음 한 작업.
```

공급자·비용·개발 작업자·운영 복원 등 후속 범위는 `BUILD_DECISIONS.md`를 따른다. 최초 코어 연결과 앱 검증을 위해 무제한 API 호출이나 대규모 동시 작업부터 활성화하지 않는다.
