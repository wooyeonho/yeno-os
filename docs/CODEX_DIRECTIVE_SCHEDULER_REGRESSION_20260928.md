# CODEX 지시서 — scheduler-fix.test.mjs 전체 회귀 실패 진단 (2026-09-28)

## §0 배경 (사실관계만)

§115 보고에서 사용자 지정 전체 회귀(`npm.cmd test`)가 **1,235건 중 1,213 통과 / 1 실패 / 21 스킵, 종료 코드 1**로 나왔고, 유일한 실패는 `runtime/test/scheduler-fix.test.mjs`이며 단독 재실행에서도 재현됨을 내가 직접 파일을 읽어 독립 검증했다(`build-artifacts/living-20260927/oss-channels-full-regression.txt` SHA-256 `02e80017829edc6845d315e5152ba56a0b9ecfc60de163760732c5e5f67db2f1` 재계산 일치, 1047/1250/1259/1260행에서 실패 재확인).

이 지시서는 새 기능이 아니라 **기존 회귀를 초록으로 되돌리는 진단·수정** 작업이다. "최상급"을 자처하려면 재현 가능한 실패를 방치한 채로는 안 된다는 소유자 취지에 따라, 이번 세션에서 새로 쓴 다른 지시서(S1+, G1)보다 먼저 처리할 것을 권고하되 우선순위 결정은 Codex/소유자 재량이다.

`runtime/test/scheduler-fix.test.mjs` 직접 읽음(109줄): 두 번째 테스트(`scheduler exception injection...`)가 의심 지점이다 — `pre.save()`로 17MiB짜리 이벤트를 담은 state를 디스크에 먼저 쓰고, `setup()`이 그 state를 로드하며 서버를 기동한 뒤, 최대 200회 × 20ms(=4초) 폴링 루프 안에 `autopilot.retryAt`이 기록되기를 기다린다. §115가 관찰 RAM 여유 0.53GiB를 언급했고 직접 원인으로 단정하지 않는다고 정직하게 적었다 — 그 판단을 존중해 이 지시서는 "무엇이 원인인지 확정하지 말고 먼저 증거로 구분하라"고 요구한다.

## §1 첫 단계 — 원인 구분 (수정 전에 먼저)

코드를 고치기 전에 다음 두 가설을 실제로 구분할 것:

- (가설 A) 진짜 스케줄러 회귀: `tick()`의 `try{...}finally{schedule()}` 로직 자체가 깨졌다(예: 17MiB state 로드 후 스케줄러가 실제로 멎거나 `runAutopilot()` 호출 경로가 바뀌었다).
- (가설 B) 환경/자원 압박 플레이크: 이 PC의 여유 RAM(통상 0.4~0.7GiB)에서 17MiB JSON을 반복 파싱·저장하는 비용이 4초 폴링 예산을 넘겨서 생기는 타임아웃이며, 스케줄러 로직 자체는 정상이다.

구분 방법 (둘 다 실행하고 실제 로그를 남길 것, 추측 금지):
1. `runtime/test/scheduler-fix.test.mjs` **단독** 3회 연속 실행(다른 무거운 프로세스 동시 실행 없이, 여유 RAM을 직전에 실측해 기록). 3회 모두 실패/1회만 실패/전부 통과 중 무엇인지 정확히 기록.
2. 두 번째 테스트 안에 임시 진단 로그(타임스탬프 포함)를 넣어 `setup()`이 실제로 몇 ms 걸리는지, 200회 폴링 루프가 실제로 몇 회 만에 `retryAt`을 관찰하는지(또는 200회 다 돌고도 못 찾는지) 측정 — §115가 이미 "pre.save() 완료 후 start() 완료 전에 중단"이라고 관찰한 지점을 정확한 숫자로 재확인. 진단 코드는 확인 후 원복(이미 §115가 했던 방식과 동일).
3. 가설 B가 맞다면(자원 압박) — 테스트의 4초 예산(200×20ms) 자체가 이 PC에서 비현실적인지, 아니면 실제로 서버 기동이 유독 느려진 별도 원인이 있는지 구분. 임의로 타임아웃 숫자만 늘려서 통과시키는 미봉책은 §7에서 명시적으로 금지.

## §2 수정 범위

- 가설 A로 확인되면: `runtime/server.mjs`의 `tick()`/`schedule()` 로직을 실제로 무엇이 깨뜨렸는지 `git log`/`git diff`로 최근 변경 이력 대조 후 수정. 이 세션에서 새로 추가된 의존성(`wilson-score-interval`, `quantum-circuit`)이나 새 파일(`gap-scout.mjs`, `openclaw-bridge.mjs`, `obsidian-rest-search.mjs`)이 원인일 가능성도 배제하지 말고 실제로 대조할 것 — 무관하다고 추정만 하지 말고 확인.
- 가설 B로 확인되면: 테스트 자체의 비현실적 시간 예산을 정직하게 넓히는 것은 허용되나(예: 200×20ms → 실측 기반의 더 넉넉한 값), **왜 그 값이 이 환경에서 근거 있는 숫자인지** 테스트 파일 주석에 실측 근거와 함께 남길 것. 그냥 숫자를 키우기만 하고 이유를 안 남기는 것은 금지.
- 어느 쪽이든 `runtime/lib/autopilot.mjs`, `runtime/server.mjs`의 스케줄러 계약(`try{...}finally{schedule()}`) 자체의 의미를 바꾸지 않는다 — 이 계약은 a847357 커밋에서 이미 확정된 버그 수정이며, 이번 작업은 그 계약을 검증하는 테스트의 신뢰성 문제를 다루는 것이지 계약 자체를 재설계하는 것이 아니다.
