# CODEX 지시서 — 오픈소스 조립 (OSS Assembly): 직접 만들기 전에 가져오고, 블랙홀 고유 부분만 직접 만든다

작성: 2026-09-30 Claude(Cowork) · 대상: Codex · 위치: 목표헌장 P1.5 이후 병행 적용(부록 B)
소유자 지시 원문 취지: "스타 많은 오픈소스는 코드 그대로 가져와서 쓰면 되는데 굳이 빌드를 시키고 있다. 성공한 오픈소스들을 이어붙이면 된다."

## 0. 원칙

1. **직접 만들기 전에 먼저 찾는다.** 새 기능을 짜기 전에 "이미 성공한 오픈소스가 있는가"를 확인한다. 있으면 가져오고, 없을 때만 만든다.
2. **직접 만드는 것은 "기준과 정의"뿐이다. 엔진은 전부 오픈소스 후보를 먼저 본다.** 고유 모듈(영수증 검증 `outcome-verification`, 욕망 `drive-state`·HUNGER_RULES, 그림자군단 `shadow-army`·`solo-leveling`, JEV, 복구 `recovery-*`, 소유자 승인 경로)도 둘로 쪼갠다.
   - **정책층(직접 제작)**: 무엇을 증거로 인정하는가(TYPE_AUTHORITY, 출처 종류), 칠죄종 정의·문턱·배부름 규칙, 그림자 등급·소환 정책, JEV 판정 기준, 소유자 승인 조건, 원문 개념 강도. 이것이 블랙홀을 블랙홀로 만드는 부분이고 어느 오픈소스에도 없다.
   - **엔진층(오픈소스 우선)**: 해시 체인·서명·투명 로그·증명 검증, 상태 기계·내구 실행·재시작 복구, 멀티 에이전트 오케스트레이션, 승인(휴먼 인 더 루프) 흐름, 스케줄링, 저장·동기화. 정책층은 엔진 위에 얇은 설정/규칙으로 얹는다.
   - 엔진 후보의 이름은 근거 검증기로 확인하기 전까지 가설이다(예: 영수증 투명 로그 계열, 내구 워크플로우 계열, 멀티 에이전트 프레임워크 계열).
   - 예외: 동결 3파일(`solo-leveling.mjs`, `recovery-one-of-qpu.mjs`, `static-guard.mjs`)은 동결이라 교체 대상이 아니다. 그 주변에 얇은 어댑터로 붙이는 것까지만 허용.
3. **외부 부품의 출력은 전부 블랙홀의 막(membrane)을 통과한다.** 오픈소스가 낸 결과는 `source: oss:<이름>@<고정 sha>`, `verificationStatus: unverified`로 들어오고, 기존 `outcome-verification`의 검증을 거쳐야 성과·등급·배부름에 쓰인다. 모델이든 오픈소스든 그 자체가 권위가 되는 일은 없다(기존 TYPE_AUTHORITY 불변).
4. **스타 수는 신뢰 근거가 아니다.** 스타·라이선스·아카이브·최근 커밋은 웹 검색 결과를 믿지 않고 독립 근거 검증기(`repository-evidence.mjs`)로 직접 확인한 값만 쓴다. 확인 못 하면 `unknown`.

## 1. 등급 규칙 (가져오는 방법)

| 등급 | 조건 | 방법 | 소유자 승인 |
|---|---|---|---|
| A 복사·개량 | 라이선스 MIT/Apache-2.0/BSD/ISC, 화면·계산 위주의 작은 코드, 비밀값·네트워크·파일 접근 없음 | `runtime/public/vendor/<이름>/` 또는 npm 정확 버전 고정. 커밋 sha, LICENSE, `VENDOR.md`(파일 해시) 기록. 설치 스크립트(postinstall) 자동 실행 금지 | 불필요. 기록만 |
| B 연결 | 크거나, 네트워크·계정·쿠키·파이썬/도커 등 별도 실행이 필요하거나, GPL/AGPL/LGPL/MPL처럼 섞으면 안 되는 것 | 별도 프로세스로 띄우고 커넥터 패널 뒤에서 어댑터로만 호출. 코어 코드에 링크·복사 금지 | **처음 켤 때 1회**(최종 연결 승인 게이트) |
| C 제외 | 아카이브됨, 라이선스 없음/불명확, sha·해시 확인 불가, 독립 근거 검증기로 확인 불가 | 사용하지 않음. 사유를 감사표에 기록 | — |

### 1.1 개량(가져와서 고쳐 쓰기) — 허용, 방식은 고정

오픈소스는 그대로 쓰지 않아도 된다. 블랙홀에 맞게 고쳐 써도 된다. 단 원본과 수정을 분리해서 남긴다.

1. **원본 보존**: 고정 커밋 sha의 원본 파일을 `SOURCE/`(해시 목록 `SOURCE_SHA256.txt`)에 그대로 둔다.
2. **수정은 패치로**: 고친 내용은 `patches/*.patch`(또는 `adapted/`의 수정본 + 원본 대비 diff)로 남기고 `ADAPTED_SHA256.txt`에 수정본 해시를 기록한다. 이미 `thinking-orbs`가 이 방식(`SOURCE_SHA256.txt`, `ADAPTED_SHA256.txt`, `adapted/`, `VENDOR.md`)이므로 동일하게 간다.
3. **변경 기록**: `VENDOR.md`에 무엇을 왜 바꿨는지 한 줄씩(Apache-2.0은 변경 고지 필수, MIT/BSD는 저작권·라이선스 고지 유지). LICENSE·NOTICE 파일은 절대 삭제하지 않는다.
4. **상류 업데이트 가능**: 새 버전이 나오면 원본을 교체하고 패치를 다시 적용해 시험한다. 패치가 안 붙으면 §에 BLOCKED로 기록(조용히 포크를 굳히지 않는다).
5. **GPL/AGPL/LGPL**: 고쳐 쓰는 것 자체는 가능하지만 수정본을 **배포**하면 같은 조건으로 소스를 공개해야 한다. 지금은 개인용이라 문제없으나, S20 공개 준비 전에 이 항목을 재검토 대상으로 표시한다. 코어에 섞지 않고 B(별도 프로세스)로만 둔다.
6. **개량의 범위**: 블랙홀 정책(증거 인정 기준, 욕망 정의, 승인 조건)을 넣기 위한 수정, 성능·안전 수정, 한국어화는 자유. 정책의 의미를 바꾸는 수정은 안 된다(기존 시험이 보증).
7. **출력 표식**은 수정본이어도 `source: oss:<이름>@<원본 sha>+patched:<수정본 해시 앞 12자리>`로 남긴다.

**B 등급의 라이선스 주의:** 별도 프로세스로 띄우는 것은 코드를 섞지 않는다는 점에서 도움이 될 뿐, GPL/AGPL 의무를 자동으로 없애지 않는다. 특히 AGPL은 수정본을 네트워크로 타인에게 제공하면 소스 제공 의무가 생길 수 있다. 개인 로컬 사용·무수정인지, 공개 단계에서 어떻게 달라지는지를 감사표 항목마다 적는다(법률 자문 아님, 불명확하면 C 또는 소유자 질문).

**B 등급의 자원 주의:** 후보의 공식 문서 최소 사양을 확인하고 이 PC의 실제 여유 메모리를 실측한 값으로만 "가볍다"고 쓴다. 실측 전에는 가벼운 후보로 확정하지 않는다.

B 등급 프로세스는 상태 폴더, `connector-secrets.dpapi`, Vault, 쿠키 저장소에 접근하지 못하게 작업 폴더와 환경변수를 분리한다. 필요한 키는 기존 커넥터 비밀값 경로로만, 소유자가 지정한 것만 전달한다.

## 2. 단계

### AUD-1. 감사 (먼저)
- 분류에는 `policy`(정책층)와 `engine`(엔진층)을 구분해 쓴다. 고유 모듈도 정책 줄과 엔진 줄을 나눠 기록하고, 엔진층은 후보를 찾는다.
- 대상: `runtime/lib/*.mjs` 전체(현재 126개 파일)와 `runtime/public/*.mjs`(28개), `scripts/`의 제품 관련 파일.
- 출발점: `docs/OSS_CANDIDATE_MAP_20260930.md`(Claude가 개념·엔진별로 모은 후보 지도, 가설). 모든 행을 근거 검증기로 다시 관측하고 코드를 읽어 확정·기각한다. 차이가 있으면 Codex 관측값이 우선이고 §에 남긴다.
- 산출: `docs/OSS_ASSEMBLY_AUDIT.md`(사람이 읽는 표) + `build-artifacts/oss-audit/audit.json`. 모듈마다 기록: 파일, 줄 수, 분류(policy / engine / commodity / mixed — 파일 안 정책 줄과 엔진 줄 비율 포함), 하는 일 한 줄, 대체 후보(이름, 라이선스, 스타, 아카이브 여부, 최근 커밋 — 전부 근거 검증기 관측값 또는 `unknown`), 등급(A/B/C), 교체 난이도, 영향 받는 시험 파일, 위험.
- 감사표의 모듈 수는 실제 파일 수와 일치해야 한다(누락 금지). 분류 근거는 코드를 읽고 쓴다(파일 이름만 보고 분류 금지).
- 먼저 검토할 후보 영역(이름 추정일 뿐, 코드로 확인 후 분류): 모델 라우팅(`model-router`, `brain-routing`), 브라우저 조작(`browser-harness`, `browser-adapter`, `browser-decision`), 에이전트 실행 뼈대(`agent-engine`, `persistent-bots`, `autopilot`), 리서치·검색(`research`, `sources`), 기억·동기화(`memory-supabase-adapter`, `memory-sync-outbox`), 음성·영상(`gemini-live`, `video`), 예약 실행, 백업.
- 근거 검증기 호출은 하루 20회 예약 예산 안에서 나눠서 한다. 예산이 부족하면 나머지는 `unknown`으로 두고 다음 날 이어간다. 예산 초과로 사실을 만들어내지 않는다.

### AUD-2. 신규 작업 OSS-first 검사 (감사와 동시에 즉시 적용)
- 앞으로 S9~S20을 포함해 새 기능을 짜기 전에 `docs/OSS_FIRST_CHECKS.md`에 한 항목씩 남긴다: 필요한 기능, 후보(검증된 메타데이터), 결정(A/B/C/직접 제작), 직접 제작이면 그 이유(블랙홀 고유인가).

### AUD-3. 교체 (감사 결과를 본 뒤, 모듈 하나씩)
- 교체 후보는 감사표에서 "효과 큼 × 위험 작음" 상위 2~3개만 첫 대상으로 고른다. 고른 이유를 §에 기록한다.
- 교체 전: 대상 모듈과 관련 시험 파일의 해시 스냅샷을 `build-artifacts/oss-audit/pre-<module>/`에 저장한다(커밋이 아직 없으므로 되돌릴 근거).
- 교체 방법: **어댑터 인터페이스 뒤에 오픈소스를 붙이고, 기존 구현은 같은 단계에서 지우지 않는다**(폴백 유지). 전체 회귀가 기존과 같거나 더 나은 통과 수로 끝난 뒤의 다음 단계에서만 기존 구현 제거를 제안한다.
- 기존 시험을 약화하지 않는다(단언 삭제·완화 금지). 시험이 구현 내부에 묶여 있어 그대로 못 쓰면 어떤 단언이 어떤 이유로 새 경계로 옮겨졌는지 표로 남긴다.
- 동결 3파일(`solo-leveling.mjs`, `recovery-one-of-qpu.mjs`, `static-guard.mjs`)은 건드리지 않는다. 해시 불변을 매 단계 확인한다.
- 한 단계에 모듈 하나. 전체 회귀는 교체 단계마다 돌린다(티어 러너 사용 후 마지막에 전체).

### 2.1 깨지면 고쳐서 돌아가게 만든다 (멈추지 않는다)

- 완료의 정의는 **실제로 기동·실행되어 시험이 통과한 상태**다. 교체·개량 중에 시험이 깨지면 보고하고 멈추는 것이 아니라 구현(어댑터·패치)을 고쳐서 통과시킨다. 시험을 고쳐서 통과시키는 것은 금지(단언 약화 금지는 그대로).
- 같은 원인으로 3번 실패하면 원인을 다시 분석해 다른 방법(다른 후보, 다른 어댑터 경계, 패치 범위 축소)을 시도한다. 그래도 안 되면 기존 구현(폴백)으로 되돌려 **서비스가 돌아가는 상태를 유지한 채** 그 항목만 BLOCKED로 기록하고 다음 모듈로 넘어간다. 하나가 막혔다고 전체가 서지 않는다.
- 실제로 돌아가는 것을 보여준다: 교체마다 기동 → 실제 호출 → 결과 해시를 §에 남기고, 화면이 바뀌면 스크린샷 경로도 남긴다. "설계했다/복사했다"는 완료가 아니다.
- 소유자 승인이 필요한 자리(B 등급 처음 켜기, 키 입력)에서만 기다린다. 그 외에는 기다리지 않는다.

## 3. 어댑터 계약 (최소)

- 이름, 고정 버전/sha, 등급, 입력·출력 스키마, 타임아웃, 메모리·CPU 제한, 네트워크 허용 호스트 목록.
- 출력 표식: `source: oss:<이름>@<sha>`, `verificationStatus: unverified`.
- 실패 시 `status: not_ok`와 원인을 돌려준다. 성공한 척하는 대체 출력을 만들지 않는다.
- 호출과 결과는 기존 요청 원장·커넥터 영수증에 남긴다.

## 4. 하지 말 것

- 정책층(증거 인정 기준, 욕망 정의·문턱, 그림자 정책, JEV 기준, 승인 조건)을 오픈소스 기본값으로 바꾸는 것. 엔진 교체는 허용하되 정책의 의미가 달라지면 안 된다(같은 입력에 같은 판정 — 기존 시험이 이를 보증).
- 스타·인기·릴 주장을 근거로 채택. 근거 검증기 관측값 없이 A/B 등급 부여.
- 복사만 해놓고 "작동한다"고 보고. 실제 실행 시험과 출력 해시가 있어야 작동이다.
- 설치 스크립트 자동 실행, 쿠키·계정 생성, 소유자 전용 자격증명 경로 변경.
- 기존 구현을 폴백 없이 즉시 삭제.

## 5. 수락 기준

1. `OSS_ASSEMBLY_AUDIT.md`가 모든 `lib`/`public` 모듈을 분류했고 모듈 수가 실제 파일 수와 일치한다. 후보 메타데이터는 근거 검증기 관측값 또는 `unknown`이다.
2. `OSS_FIRST_CHECKS.md`가 신규 작업마다 채워지고 있다.
3. `BLACKHOLE_TARGET_ARCHITECTURE.md`가 작성되고 소유자 확인을 받았다(AUD-4).
4. 첫 교체 1건 이상: 어댑터+폴백, 출력 표식 `oss:…@sha`, 기존 시험 단언 유지(표 첨부), 전체 회귀가 기존 기준(최신 기록된 통과 수) 이상, 동결 3파일 해시 불변, 비밀값 스캔 0건.
5. 모든 단계는 `CLAUDE_EXECUTION_STATE.md`에 `§N — 날짜 Codex: 제목`으로 VERIFIED/RAN-UNVERIFIED/BLOCKED를 구분해 기록하고, 산출물 해시 목록을 붙인다. Claude가 해시·코드·시험을 직접 대조해 검증한다.

## 6. 소유자 결정 큐 (이 지시서에서 새로 생기는 것)

- B 등급 후보를 실제로 켜는 순간(프로세스 기동, 파이썬/도커 설치 포함).
- 기존 구현 제거 제안이 나왔을 때의 제거 승인.
