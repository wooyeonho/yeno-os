# 요청 재시도와 결과 보존

2026-09-10. 코어 0.2.2의 실행 식별자 보완. 실제 검사·배포 시각과 소스는 `LIVE_ACCEPTANCE.md`를 따른다.

## 계약

- Android `/api/v1/`의 등록·명령·작업·설정·제어·기기 폐기 등 쓰기는 비어 있지 않은 1–160자 `requestId`를 요구한다. 클라이언트는 전송 전에 ID와 본문을 저장하고, 응답이 불확실하면 같은 ID와 본문으로 재전송한다.
- 기존 `/api/`의 ID 없는 명령은 호환 목적으로 남아 있으며 중복 방지를 보장하지 않는다. 프로젝트·자료 쓰기와 소유자 기기 폐기는 기존대로 ID가 필수다. 새 클라이언트와 후속 작업자는 ID 없는 쓰기를 사용하지 않는다.
- 기기 등록은 페어링 인증, 나머지 native API는 기기 bearer 인증을 먼저 통과해야 한다. ID는 인증을 대신하지 않는다. 현재 단일 소유자의 기기끼리 기록을 공유하며 여러 사용자용 격리는 아니다.
- 요청 지문은 기존 방식 그대로 메서드·정규화된 경로·ID를 제외한 정렬된 JSON 본문으로 계산한다. 자기 기기 폐기만 서버가 인증한 기기 ID를 포함한 내부 경로를 사용한다. 같은 ID에 다른 요청/폐기 대상을 보내면 409이며 실행하지 않는다.

## 실행 식별자와 응답 캐시

`state.requestLedger`는 접수된 ID·지문·성공 상태·가능한 결과 참조를 최대 20,000건 보관하고 자동 삭제하지 않는다. `state.requests`의 응답 본문만 2,000건 및 직렬화된 UTF-8 JSON 2MiB 이내로 줄인다. 둘은 같은 상태 저장에 포함되며, 저장 실패 뒤 성공 응답이나 상태를 공개하기 전에 저장을 다시 완료해야 한다.

캐시가 남아 있으면 원래 응답을 반환한다. 캐시가 없으면 같은 작업·기억·기기·프로젝트·자료 ID의 현재 공개 상태를 반환한다. 따라서 ID는 같지만 상태·버전은 원래 접수 시점과 다를 수 있다. 입력·중간 초안·기기 인증 해시는 복구 응답에 넣지 않는다. 기기 등록 토큰은 원본 등록이 유효할 때만 복구한다.

스냅샷/제어 응답처럼 재구성할 수 없거나 대상이 없으면 410 `REQUEST_RECEIPT_EXPIRED`를 반환한다. 이는 이미 접수된 요청이다. 새 ID를 자동 발급하지 말고 상태와 실제 결과를 확인한다. 인증된 `GET /api/v1/requests/<URL-encoded requestId>` 또는 소유자용 `/api/requests/...`는 `{request:{requestId,status,cached,reference}}`만 반환한다. 원문 요청·응답·지문·비밀값은 포함하지 않는다. 알 수 없는 ID는 404다.

## 용량과 멈춤

20,000건을 채우면 새 ID의 일반 작업은 실행 전에 507 `REQUEST_LEDGER_CAPACITY`로 거부한다. 기존 ID 조회/재시도는 가능하다. 인증된 전체 멈춤과 기기 폐기는 용량과 관계없이 수행하되, 새 ID를 보관하지 못하면 `receiptPersisted:false`를 반환한다. 이 예외는 작업을 시작하지 않는 안전 동작에만 적용한다. 용량 확보를 위해 원장을 임의 삭제하지 않는다. 상한 확대나 트랜잭션 저장소 이전은 데이터·복원 검증을 동반한 후속 변경이다.

상태 API의 `requestTracking`은 현재 ID 수·상한·캐시 수·바이트 상한을 보여준다. 이것은 무한 저장이나 외부 작업의 exactly-once 실행 보장이 아니다. 후속 개발 작업자의 프로세스 실행·외부 쓰기·불명확한 결과 조정은 별도로 연결하고 검증한다.

## 이전 데이터와 클라이언트

기존 상태에 원장이 없으면 아직 보관 중인 응답의 지문을 그대로 가져온다. 이전 코어가 이미 지운 ID는 복구할 수 없다. 과거 백업의 원장 없는 형식도 읽을 수 있고, 새 백업은 원장을 함께 암호화한다. 기존 원장이 잘못됐다면 비우지 않고 유효한 이전 상태로 복구하거나 시작을 중단한다. 과거 백업 생성 이후의 ID, 손상 후 `.bak`로 돌아가며 잃은 최신 ID까지 보장하지 않는다.

이 변경보다 오래된 코어는 원장 보존 규칙을 지키지 않는다. 이전 실행 파일을 새 상태의 writer로 사용하지 않는다. 롤백은 원장 처리를 유지한 수정 버전과 별도 복원 검사로 진행한다.

웹 요청 처리와 native 소스는 401·403·408·410 및 5xx 뒤 대기 ID를 유지한다. 기존 설치 APK에는 소스 수정이 자동 전달되지 않으며 새 APK 빌드·설치 전까지 이 추가 처리는 미적용이다. 코어의 기존 APK 문서 명령 호환성 검사는 실제 폰 확인과 구분한다.

## 검사 범위

단위 검사는 2,000건 초과 캐시 정리·2MiB 제한·20,000건 용량·상충 지문·특수 ID·마이그레이션·공개 결과 복구를 확인한다. 통합 검사는 실제 HTTP, 새 Node 프로세스 재시작, 암호화 다운로드·새 디렉터리 복원, 원장 용량에서 새 작업 차단과 멈춤/폐기를 확인한다. 용량 통합 검사는 정지된 코어에 준비한 유효한 20,000개 ID를 사용하며 20,000회 실사용 부하 시험은 아니다.
