# YENO OS — 실제 빌드 설계와 최초 구현 지시서

작성일: 2026-09-08

이 파일은 제작 결정과 구현 지시서다. APK·EXE 또는 배포 완료 보고서가 아니다. 이번 작업에서는 기존 실행 코드를 읽고 빌드 경로를 검토했으며, 새 네이티브 앱이나 클라우드 서버를 구현·배포하지 않았다.

## 1. 무엇을 만드는가

연호님이 평소 다른 일을 하다가 폰이나 노트북으로 확인하고 통제할 수 있는 개인 OS를 만든다. 여행 중 사용은 그중 한 장면이다.

최종 형태는 Android APK, Windows 설치 EXE, 상주하는 클라우드 실행 코어다. 세 구성은 같은 소유자·기억·목표·작업 기록을 공유한다. Windows와 Android 위에서 실행되는 개인 운영 계층이며, 두 기기의 기존 커널을 교체하는 프로젝트는 아니다.

첫 성공 장면:

> 폰에서 일을 맡긴다. 앱을 닫고 다른 일을 한다. 다시 열면 실제 작업 상태와 결과 파일이 보인다. 멈춤과 재개가 작동하며, 연결이 끊겼으면 마지막 확인 시각이 표시된다.

두 번째 성공 장면:

> 허용한 프로젝트에 작은 기능을 추가하라고 맡긴다. YENO가 코드를 수정하고 시험한다. 실패하면 정한 범위에서 고친다. 결과 소스와 시험용 설치 파일을 만들어 알린다.

## 2. 현재 사실과 아직 없는 것

| 항목 | 이번에 확인한 상태 |
|---|---|
| 기존 실행 코어 | Node 기반 0.1.1 소스가 있음 |
| 기억·검색·작업 제어 | 기본 구현이 있음 |
| 이전 검증 | 전달 문서에 Linux / Node 24.19.0, 19개 통과 기록이 있음. 이번 설계 검토에서 다시 실행한 결과는 아님 |
| AI | 선택적으로 초안을 생성하는 HTTP 호출 코드가 있음. 자유 명령을 도구 실행으로 연결하는 루프는 아직 없음 |
| 앱 | Tauri 프로젝트, APK, 새 Windows 설치 EXE는 아직 없음 |
| 상주 서버 | 실제 배포 주소와 배포 완료 증거가 없음 |
| 개발 AI | 현재 작업 환경에는 Codex CLI와 Claude Code CLI가 설치되어 있지 않음. 이번에 두 CLI를 실행했다고 주장하지 않음 |
| 빌드 환경 | 현재 환경에 Node와 Java는 있지만 Rust/Cargo와 Gradle 실행 파일은 확인되지 않음 |
| 저장소 | 연결된 GitHub에서 yeno, jarvis, homunculus 이름 검색으로 목표 저장소를 찾지 못함. 다른 이름이거나 연결 범위 밖일 수 있음 |

기존 UI는 `/api/...` 상대 주소를 사용하고 연결 키를 sessionStorage에 저장한다. 서버는 같은 출처와 지정 프록시를 검사한다. 따라서 웹 파일을 그대로 APK에 넣는 것만으로 네이티브 앱 연결·인증 유지가 완성되지 않는다.

기존 JSON 저장소는 단일 프로세스 잠금을 사용한다. 이 저장소를 여러 서버 복제본이 동시에 쓰게 배포하지 않는다. 기존 노트북의 0.2.3 설치와 이번 재구축 0.1.1은 별도 계보로 취급한다.

## 3. 선택할 구조

| 구성 | 선택 | 책임 |
|---|---|---|
| 소스 | 연호님 계정의 비공개 GitHub 저장소 하나 | 코드·변경 기록·빌드 정의·검사 결과 관리 |
| 개발 | Codex Cloud 중심 | 작업별 코드 수정과 검증, 검토 가능한 변경 제출 |
| 공용 앱 | Tauri 2 + 기존 HTML/CSS를 바탕으로 한 TypeScript UI | APK·EXE의 명령, 기억, 작업 상태, 결과, 통제 화면 |
| 실행 코어 | Node/TypeScript | 인증, 목표, 도구 호출, 작업 상태, 예산, 이벤트 처리 |
| 초기 영속 저장 | 단일 실행 코어 + SQLite 및 결과 파일 볼륨 | 트랜잭션으로 작업 접수·비용 예약·상태 저장. 기존 JSON은 검증 후 마이그레이션 |
| 운영 서버 | 영속 디스크가 있는 Linux 호스트 하나에서 시작 | 앱이 닫혀도 맡긴 서버 작업을 계속 처리 |
| 개발 작업자 | 작업별 격리된 환경, 초기 동시 실행 1개 | 허용된 저장소 사본에서 코드 수정·시험 |
| 설치 파일 빌드 | GitHub Actions의 Windows 작업과 Android 작업 | 같은 소스 커밋에서 EXE·APK 생성 |
| PC 작업자 | 귀국 후 Windows에서 연결 | 허용한 PC 폴더·프로그램 실행 |

호스팅 업체는 아직 정하지 않았다. 기존 계정의 사용 가능 자원, 실제 비용과 지속 실행 조건을 확인한 뒤 하나를 정한다. 이 문서는 새 결제나 서버 개설을 실행하지 않는다.

SQLite와 결과 파일을 쓰는 초기 운영은 실행 코어 1개로 제한한다. 읽기 UI와 개발 작업자는 분리할 수 있지만 저장소 파일을 공유하는 여러 제어 서버를 띄우지 않는다. 확장이 실제로 필요해지면 Postgres 등으로 이전한다.

Codex Cloud는 소스 작업을 수행하는 개발 환경이다. YENO 운영 서버는 따로 둔다. Codex SDK를 YENO 개발 작업자에 연결하면 그 작업자가 실행되는 호스트에서 코딩 작업을 수행한다. 이것을 Codex Cloud 작업을 시작하는 API와 혼동하지 않는다. [Codex Cloud](https://learn.chatgpt.com/docs/cloud), [환경 구성](https://learn.chatgpt.com/docs/environments/cloud-environment), [Codex SDK](https://learn.chatgpt.com/docs/codex-sdk)

## 4. APK와 EXE를 실제로 만드는 과정

### 4.1 공용 앱 작성

Tauri 2 프로젝트를 만들고 앱 주소, 기기 인증, 명령 접수, 상태 표시를 구현한다. UI의 API 주소를 명시적으로 구성하며, 기기 인증 정보는 각 운영체제의 보안 저장 기능과 연결한다. 공급자 API 키와 빌드 서명 키를 앱에 넣지 않는다.

첫 화면에는 다음 다섯 가지가 있다.

1. 진행 중: 작업명, 현재 단계, 마지막 진행 시각.
2. 완료: 실제 결과 파일과 열기 버튼.
3. 결정 필요: 질문 하나와 판단에 필요한 결과.
4. 다음 작업: 맡긴 목표와 우선순위.
5. 통제: 일시정지, 취소, 재개, 버전 복원.

첫 APK의 범위는 연결·명령·상태·결과·통제다. 홈 화면 위젯, 공유 메뉴, 음성 버튼, PC 트레이와 창 확대·축소는 이 흐름이 실제 기기에서 통과한 다음 붙인다. 작은 화면에서 기본 명령을 사용할 수 있어야 한다.

### 4.2 Windows 빌드

GitHub Actions의 Windows 실행 환경에서 Node, Rust/MSVC, Tauri 요구 도구를 준비한다. 의존성 잠금 파일을 사용하고, 소스 검사 후 NSIS 설치 EXE를 만든다. 앱에 필요한 런타임은 설치본에 포함하거나 설치 과정에서 명확하게 처리해서 사용자가 개발 도구를 별도로 설치하지 않도록 한다.

Tauri 프로젝트와 빌드 설정이 만들어진 이후의 명령 예:

```bash
npm ci
npm run tauri build -- --bundles nsis
```

이 명령은 현재 0.1.1 폴더에서 바로 실행되는 명령이 아니다. 해당 폴더에는 아직 Tauri 프로젝트와 `tauri` 스크립트가 없다. Windows CI에서 직접 빌드하는 경로를 우선한다. [Windows 설치 파일](https://v2.tauri.app/distribute/windows-installer/)

Windows 앱의 최초 범위는 클라우드 연결이다. PC 파일·프로그램 실행 작업자는 별도 단계에서 추가한다. 클라우드 연결 앱이 빌드됐다는 이유로 PC 조작까지 구현됐다고 표시하지 않는다.

### 4.3 Android 빌드

별도 Linux CI 작업에 Node, Rust, 호환되는 JDK, Android SDK/NDK를 준비한다. 프로젝트 초기화 때 Android 프로젝트를 생성하고 버전 관리한다. SDK, NDK, JDK, Rust, Node, 패키지 버전을 빌드 기록에 남긴다.

Tauri 프로젝트와 Android 구성이 준비된 이후의 명령 예:

```bash
npm ci
npm run tauri android build -- --apk --target aarch64
```

초기 대상은 연호님의 실제 Android 폰이다. 생성된 APK의 패키지 ID·버전·서명을 검사하고, 실제 폰 설치를 따로 확인한다. 개인 설치용 APK와 Play 배포용 AAB를 혼동하지 않는다. [APK 빌드](https://v2.tauri.app/distribute/google-play/), [빌드 전제 조건](https://v2.tauri.app/start/prerequisites/)

테스트용 서명과 정식 업데이트에 사용할 서명을 구분한다. 반복 설치에서 같은 앱으로 업데이트하려면 서명 정책과 버전을 유지해야 한다. 정식 서명 키와 복구 사본은 연호님이 소유하고, 비밀 저장소에서 빌드에 주입한다. 서명 키는 소스 ZIP에 넣지 않는다. [Android 서명](https://v2.tauri.app/distribute/sign/android/)

Tauri의 데스크톱 GitHub Actions 예시를 Android CI까지 완성된 것으로 취급하지 않는다. Android 작업은 별도로 구성하고 실제 실행한다. [Tauri GitHub Actions](https://v2.tauri.app/distribute/pipelines/github/)

### 4.4 결과 전달과 확인

각 빌드는 다음 결과를 남긴다.

- 소스 커밋, 빌드 실행 ID, 플랫폼과 도구 버전.
- APK 또는 EXE, 파일 크기와 SHA-256, 서명 상태.
- 실행한 검사와 결과, 생략·실패·미검증 항목.
- 설치·업데이트·이전 버전 복원 방법.

비공개 저장소의 빌드 결과로 전달하고, 개인 운영 저장소에 보관할 배포본은 별도로 관리한다. 빌드 로그의 임시 보존 기간을 유일한 백업으로 삼지 않는다. 이후에는 YENO에서 빌드 작업 상태와 결과를 조회하도록 연결한다.

APK 빌드 성공, 폰 설치 성공, 실제 명령 성공, 일상에서 계속 사용 가능은 각각 별도의 상태다. 처음 두 가지가 성공했다고 나머지를 완료 처리하지 않는다.

## 5. 매번 대화창에 오지 않아도 움직이는 방법

모든 장기 작업은 먼저 작업 ID와 함께 영속 저장한다. 접수 응답이 유실되면 같은 ID로 조회·재시도해 중복 작업을 막는다.

실행 코어는 목표, 완료 조건, 허용된 프로젝트·도구, 예산, 최대 재시도, 중단 조건을 읽는다. 필요한 때 모델에 판단을 요청하고 실제 도구 실행 결과를 다시 전달한다. 완료 판단에는 결과 파일과 검사 증거를 요구한다.

기본 흐름은 접수 → 계획 → 실행 → 검증 → 완료다. 중간에 일시정지, 기기 연결 대기, 소유자 결정 대기, 실패 상태로 이동할 수 있다. 화면에는 서버에서 확인한 사실을 표시하고 가짜 진행률을 넣지 않는다.

앱을 닫아도 서버에 접수된 작업은 계속된다. 노트북이 꺼졌다면 PC에서만 가능한 일은 대기 상태다. Android 앱의 무제한 백그라운드 실행에 장기 작업을 의존하지 않는다. [Android 백그라운드 작업](https://developer.android.com/develop/background-work/background-tasks)

연호님이 반복 업무의 시간·조건·범위를 등록하면 해당 사건에 반응한다. 대기 중에는 사건과 실행할 작업을 확인하고, 이유 없이 모델을 계속 호출하지 않는다. 이번 문서 작성으로 새 예약 작업이나 알림을 등록하지 않았다.

알림은 완료, 결정 필요, 중요한 실패, 한도 도달에 집중한다. 알림이 유실돼도 앱을 열어 서버의 최신 상태를 확인할 수 있어야 한다. 전송 실패와 업무 실패를 구분한다.

## 6. 개발 AI 역할

| 역할 | 담당과 범위 |
|---|---|
| 현재 설계와 통합 | 이 대화에서 요구사항·설계·소스 변경·검증 결과를 검토 |
| 첫 개발 실행 | Codex를 기본으로 연결. 하나의 실제 개발 작업을 끝까지 검증 |
| 중요한 계획·검토 | Astra를 선택 가능한 검토 모델로 사용. 실제 사용 권한과 모델 이름은 연결 시 확인 |
| 두 번째 개발 도구 | Claude Code가 필요한 작업을 분리해 추가. 도입 전 실제 인증·실행·취소·결과 수집을 검증 |
| 최종 결정 | 연호님. 맡긴 범위 안의 세부 실행은 위임하고 범위 변경과 운영본 적용을 결정 |

모델과 개발 제품을 같은 개념으로 취급하지 않는다. YENO는 공급자를 바꿀 수 있는 연결 계층을 두고, 기억과 작업 기록을 특정 모델 대화에만 저장하지 않는다.

초기에는 개발 작업자 하나로 시작한다. 역할 목록을 48개 둘 수 있어도 48개의 무거운 프로세스를 동시에 띄우겠다고 약속하지 않는다. 동시 실행 수는 실제 메모리·시간·비용 측정으로 늘린다.

ChatGPT에서 보이는 도구와 계정 권한이 APK에 자동으로 복사되는 구조가 아니다. YENO가 사용할 모델과 외부 도구에는 별도의 실제 연결·인증이 필요하다. 구독에 무엇이 포함되는지와 API·호스팅·CI의 실제 비용은 계정에서 확인한다.

## 7. 연호님만의 YENO를 만드는 요소

세상에 비슷한 기능이 전혀 없다는 보장은 할 수 없다. 연호님의 계정과 기기에 연결된 개인 인스턴스, 누적된 기억·결정·작업 방식, 연호님 소유의 코드와 복구 자료로 고유성을 만든다.

| 개인 자산 | 구현할 내용 |
|---|---|
| 정체성 | 이름 YENO, 소유자 식별자, 말투·보고 형식, 변경 이력 |
| 기억 | 출처·시각·수정 이력이 있는 사실, 선호, 결정, 프로젝트 기록 |
| 목표 | 지금 맡긴 일, 장기 목표, 우선순위, 완료 기준 |
| 작업 방식 | 반복해서 성공한 절차와 연호님이 고친 기준 |
| 평가 기록 | 유용했던 결과, 실패 원인, 이후 수정의 효과 |
| 소유와 이동 | 비공개 소스, 데이터 내보내기, 복구 사본, 다른 모델·서버로 이전 가능한 형식 |

실제 의식·욕망을 만들었다고 주장하지 않는다. 호문쿨루스 같은 지속성은 같은 정체성과 기억을 유지하고 맡긴 목표를 이어가는 행동으로 구현한다.

모델이나 호스팅 업체를 쓰는 동안 해당 서비스로 전달되는 정보가 있을 수 있다. 개인 전용 배포와 모든 데이터가 기기 밖으로 나가지 않는 것은 다른 조건이다. 도구별 전송 범위와 실제 사용한 자료를 기록하고, 전체 기억을 모든 호출에 보내지 않는다.

처음에는 이 대화에서 확인한 YENO 요구만 개인 설정에 반영한다. 관련 없는 가족·건강·예약 정보 등을 자동으로 수집해 넣지 않는다.

## 8. 소유자 통제와 자기 개선

작업마다 범위와 예산을 한 번 정하면 그 안의 읽기, 코드 수정, 시험, 시험용 빌드는 이어서 수행하게 한다. 새 지출, 외부 발송, 원본 삭제, 운영 버전 교체 등은 해당 작업에 이미 허용됐는지 확인한다. 기존 허용 범위를 임의로 넓히지 않는다.

전체 정지 요청은 모델의 동의를 기다리지 않는다. 작업자와 자식 프로세스에 취소를 전달하고 실제 종료 상태를 확인한다. 접속이 끊겨 정지를 전달하지 못했다면 정지 완료로 표시하지 않는다. 정지 해제 후에는 무엇을 재개할지 선택한다.

자기 개선은 다음 순서로 만든다.

1. 실패·느린 작업·반복 수정 요구에서 개선 후보를 찾는다.
2. 관련 작업 기록과 재현 방법을 확보한다.
3. 별도 환경에서 코드를 고친다.
4. 이전 버전과 동일한 입력으로 비교하고 결과를 남긴다.
5. 후보 버전과 효과·제한을 연호님에게 제시한다.
6. 허용된 적용 절차로 교체하고 실패하면 검증된 버전으로 복원한다.

코드 복원과 데이터 복원을 구분한다. DB 구조가 바뀌었으면 호환성 검사와 사전 백업이 필요하다. 이미 외부에 보낸 메시지나 완료한 거래 같은 외부 행동까지 코드 롤백으로 취소된다고 표시하지 않는다.

현재 0.1.1 스냅샷은 기억과 설정만 복원한다. 운영 코드, 모든 결과 파일, 전체 PC 복원을 구현한 것으로 취급하지 않는다.

Obsidian을 연결할 때는 먼저 읽고 분류한다. `00_INBOX_RAW` 원문은 읽기 전용이며 삭제·덮어쓰기 대상으로 삼지 않는다. 정리 초안은 `01_DRAFTS`에 새 파일로 제안하고, 링크·분류 반영은 우연호님 승인 후 진행한다. 수행 내용은 `CHANGELOG.md`에 기록하도록 한다. 현재 이 ChatGPT는 실제 Vault를 직접 읽거나 쓸 수 없으므로 필요 자료는 붙여넣기나 업로드로 받는다.

## 9. 실제 제작 순서와 완료 기준

| 순서 | 개발 결과 | 통과 조건 |
|---|---|---|
| 1 | 비공개 저장소와 기준선 | 기존 코드 보존, 기존 검사 재현, 구현·미구현 상태 문서화 |
| 2 | 상주 코어와 인증·저장 | HTTPS 연결, 기기별 인증과 폐기, 작업 접수와 기억이 재시작 후 유지 |
| 3 | 첫 APK | 실제 폰 설치 → 명령 → 실제 파일 생성 → 앱 종료·재실행 후 결과 확인 |
| 4 | 모델·비용·도구 실행 | 실제 모델 한 번 호출, 기록된 비용, 자유 명령에서 허용 도구 실행, 한도·오류 처리 |
| 5 | 첫 개발 작업자와 빌드 | 지정 프로젝트 기능 수정 → 시험 → 소스·설치 파일·검사 결과 회수 |
| 6 | 일상 사용 흐름 | 상태 조회, 알림, 입력 보관, 중단·재개, 연결 유실 때 사실 표시 |
| 7 | Windows 설치와 PC 작업 | 실제 PC 더블클릭·연결·허용 폴더 작업·종료·재시작 확인 |
| 8 | 개선과 복원 | 재현 가능한 실패 수정, 이전 버전 비교, 후보 적용·복원 시험 |

Windows 설치 파일의 CI 빌드는 APK 개발과 병행할 수 있다. 실제 Windows 확인은 노트북을 사용할 수 있을 때 진행한다. PC 시험을 기다리느라 클라우드·Android 독립 작업을 멈추지 않는다.

처음부터 모든 일을 잘하는 1.0을 선언하지 않는다. 위 단계의 실제 증거로 완성 범위를 넓힌다. 일정은 계정 연결과 첫 기기 시험을 수행한 뒤 추정하며, 현재는 특정 날짜의 완성을 보장하지 않는다.

## 10. 최초 Codex Cloud 작업에 넣을 지시문

아래는 저장소를 선택한 뒤 사용할 구현 지시문이다. 이 문서만으로 저장소 생성이나 실행이 시작되지는 않는다.

```text
YENO OS를 일상에서 사용하는 개인 OS로 구현한다.
목표: Android APK와 Windows EXE가 하나의 상주 코어에 연결되고,
사용자가 앱을 닫아도 접수된 일이 이어지며 다시 열어 결과를 확인한다.

먼저 저장소의 실제 파일과 적용되는 AGENTS.md를 읽는다.
현재 재구축 기준선은 YENO runtime 0.1.1이다.
기존 로컬 0.2.3 설치는 다른 계보이며 덮어쓰지 않는다.
기존 ZIP만 있다면 경로 탈출과 기존 파일 덮어쓰기를 막고 별도 폴더에 풀어 검토한다.
기존 코드와 검사 결과를 확인하고, 이 문서의 구현 여부를 사실대로 기록한다.

첫 구현 범위는 다음 하나의 사용 흐름이다.
실제 Android 앱 -> 인증된 코어 -> 명령 접수 -> 실제 결과 파일 생성
-> 앱 종료 -> 재실행 -> 같은 작업과 결과 확인 -> 정지/재개.
일반 문서 작업으로 먼저 전체 연결을 검증하고,
AI가 연결되지 않았으면 AI로 만든 결과처럼 표시하지 않는다.

제안 구조:
apps/controller: Tauri 2 공용 UI와 네이티브 연결
services/core: 단일 Node/TypeScript 코어
workers/developer: 후속 개발 작업 실행
workers/windows: 후속 PC 작업 실행
packages/contracts: API·작업 상태·권한 계약
docs/STATUS.md: 완료·미구현·미검증·다음 작업
docs/DEVICE_ACCEPTANCE.md: 폰/PC 실기기 확인

기존 상대 /api 주소, sessionStorage 토큰, Host/Origin 검사를
그대로 네이티브 앱에 포장하지 않는다.
API 주소와 기기 인증, OS 보안 저장, 서버의 명시적 연결 정책을 구현한다.
신규 인증/저장소는 기존 기억과 기록을 보존하는 마이그레이션이 필요하다.

영속 작업 ID로 중복 실행을 방지한다.
서버 재시작 후 상태를 복구하되 외부 실행 결과가 불명확하면
증거를 확인하기 전 자동으로 같은 행동을 반복하지 않는다.
전체 정지 해제는 개별 작업의 자동 재개로 해석하지 않는다.
UI의 진행률과 완료는 실제 서버 이벤트와 결과에 근거한다.

클라우드 개발 환경과 운영 서버를 구분한다.
외부 계정이 아직 없으면 서버 배포 설정과 정확한 필요 항목까지 작성한다.
존재하지 않는 배포 주소·인증·기기 시험 결과를 만들지 않는다.
기존 지시와 허용 범위 안에서 가역적인 구현·수정·시험은 이어서 수행한다.
별도 허가가 없는 지출이나 공개 배포는 실행하지 않는다.

CI는 검사, Windows NSIS EXE, Android APK를 각각 구성한다.
Android에는 SDK/NDK/JDK와 서명 구성이 별도로 필요하다.
잠금 파일과 도구 버전을 기록하고 결과 APK/EXE·해시·검사 로그를 수집한다.
서명 키와 모델 키를 소스나 앱 파일에 넣지 않는다.
CI 실행 전에는 '워크플로 작성', 실행 후에는 실제 결과를 보고한다.
실제 폰/PC를 확인하지 못한 항목은 미검증으로 남긴다.

AI 실행은 실제 공급자 연결과 비용 예약/정산부터 구현한 뒤 도구 루프로 확장한다.
개발 도구는 Codex 하나를 먼저 연결하고 중요한 검토에 Astra를 사용한다.
Claude Code는 실제 연결을 추가한 뒤 사용 여부와 결과를 기록한다.
앱 SDK가 Codex Cloud의 임의 작업을 호출할 수 있다고 가정하지 않는다.

Obsidian RAW는 읽기 전용, 읽기/분류 먼저, 초안은 새 파일,
링크/분류 반영은 우연호님 승인 후, 변경 내용은 CHANGELOG에 기록한다.

작업을 끝낼 때 제출할 것:
수정 파일, 실행 명령과 실제 결과, 설치 파일이 있으면 정확한 위치,
성공한 실제 사용 흐름, 아직 막힌 계정/환경/기기 조건,
다음 한 작업. 설계 설명만 하고 구현 가능한 부분을 남겨두지 않는다.
```

## 11. 계정 연결과 소유자가 확인할 부분

첫 연결은 사용할 비공개 GitHub 저장소다. 이미 있다면 정확한 주소를 받는다. 없으면 연호님 계정에서 만들고 Codex 접근 범위를 해당 저장소로 지정한다. 비밀번호나 API 키를 대화창에 붙여넣도록 요구하지 않는다.

운영 서버의 후보 설정과 비용, 실제 모델 연결에 필요한 항목은 구현 결과와 함께 제시한다. 연호님은 소유 계정 연결, 필요한 비용 결정, 폰 설치와 실제 사용 피드백을 맡는다. 여러 AI에게 같은 설명을 반복하거나 매 파일을 직접 옮기는 작업은 줄인다.

현재 약속할 수 있는 것은 구체적인 소스와 검사, 설치본 생성 과정과 사실에 근거한 상태 보고다. 계정 연결 전 배포, 실기기 확인 전 정상 작동, 시험 없는 완벽함이나 세계 유일성은 완료로 보고하지 않는다.
