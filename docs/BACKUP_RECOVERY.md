# 암호화 백업과 독립 복원

2026-09-10 요청 원장 보완: 새 백업은 `requestLedger`를 포함한다. 원장이 없는 이전 백업도 읽고 시작 시 남은 응답 캐시의 ID를 이전한다. 백업 생성 후 접수된 ID나 이전 코어가 지운 ID는 복구 대상이 아니다. 원장 보존 규칙을 모르는 이전 코어로 새 상태를 실행하지 않는다. [요청 보존 계약](REQUEST_IDENTITY.md).

범위: 실행 코어의 전체 상태와 상태에서 참조하는 실제 결과 파일. 소유자용 API와 Node 24 관리 도구다. Android 앱의 백업 버튼, 자동 주기 백업, 운영 서버의 자동 교체는 아직 없다. 실제 검사·배포 결과는 `LIVE_ACCEPTANCE.md`를 따른다.

## 포함·제외와 보관

- 포함: 기억, 프로젝트, 자료와 검토 기록, 작업 원본·체크포인트, 결과 바이트·해시, 요청 영수증, 설정·스냅샷·이벤트, 기기 메타데이터·토큰 해시.
- 제외: 페어링 원문 키, 공급자·서명 키, 환경 변수, 실행 코드, 잠금, 참조되지 않은 파일. 사용자 본문에 직접 입력된 비밀을 자동 판별·삭제하는 기능은 아니다.
- 백업은 무작위 32바이트 키와 AES-256-GCM으로 암호화한다. 12바이트 무작위 IV, 16바이트 인증 태그와 형식 식별자를 인증한다. 암호화 라이브러리는 Node 내장 crypto를 사용한다. [Node crypto 원문](https://nodejs.org/api/crypto.html#cryptocreatecipherivalgorithm-key-iv-options)
- 무압축 JSON 전체 크기 16 MiB, 결과 파일 최대 10,000개로 제한한다. 초과 시 일부만 저장하는 대신 전체 백업을 거부한다. 현재 단일 writer·소규모 코어용이다.
- 암호화 파일과 복구 키는 모두 필요하다. 복구 키는 비밀번호 관리자 등 별도 안전한 위치에도 보관한다. 같은 계정에 두 파일을 보관하는 것만으로 그 계정 탈취를 방어할 수는 없다. 소스 저장소에 넣지 않는다.

## 관리자 명령

Node 24 환경에서 저장소 루트를 작업 위치로 사용한다. 아래 경로는 예시이며 새 백업·키 파일의 부모 폴더는 미리 준비한다. Linux에서 개인 연결 파일·키·백업 권한은 `0600`, 폴더는 `0700`이다. 이번 검사는 Linux이며 Windows에서 파일 권한·디렉터리 동기화는 별도 검증이 필요하다.

```sh
node scripts/backup.mjs keygen --key-file /private/yeno-recovery.key
node scripts/backup.mjs export --connection-file /private/connection.json --key-file /private/yeno-recovery.key --output /private/yeno-backup.yenobak
node scripts/backup.mjs verify --archive /private/yeno-backup.yenobak --key-file /private/yeno-recovery.key
node scripts/backup.mjs restore --archive /private/yeno-backup.yenobak --key-file /private/yeno-recovery.key --target /private/yeno-restored-new
```

개인 연결 파일은 `origin`과 `pairingToken` 두 필드의 JSON이다. 실제 값은 소스·명령 인수·프롬프트에 넣지 않는다. HTTP는 loopback에서만 허용하며 원격은 HTTPS, 리디렉션은 거부한다. 키는 명령 인수가 아닌 파일로 읽는다. 다운로드 해시와 복호화·구조·결과 해시를 모두 확인한 뒤 새 출력 파일을 저장한다. 기존 출력 파일은 덮어쓰지 않는다.

API는 `POST /api/backups/export`이며 소유자 페어링 bearer만 허용한다. JSON에는 `encryptionKey` 하나만 받는다. 이 요청을 영수증/이벤트에 저장하지 않는다. 기기 bearer와 `/api/v1/backups/export`는 거부한다. 암호화는 기존 writer가 내구성 확인 후 동기적으로 상태·결과를 읽는 동안 수행하므로 이 과정에서 다른 코어 작업이 끼어들지 않는다. 이 범위에서 짧게 요청 처리가 지연될 수 있다.

## 복원 안전 조건

1. 복호화·형식·크기·모든 결과 해시·참조·경로 검사를 통과한 후 쓰기를 시작한다.
2. **아예 존재하지 않는 새 디렉터리**만 허용한다. 원본·실행 중 코어·기존 빈 디렉터리도 덮어쓰지 않는다. 심볼릭 링크 경로는 거부한다.
3. 결과와 상태를 디스크에 동기화한다. 복원 중 표식이 있으면 코어 시작을 거부한다. 실패한 디렉터리를 재사용하지 않고 새 경로에 다시 복원한다.
4. 복원은 전체 멈춤을 켜고, 진행 중·대기 작업을 일시정지하고 AI를 끈다. 소유자가 확인하기 전 작업을 다시 실행하지 않는다.
5. 복원 시 과거에 살아 있던 기기 토큰을 모두 폐기한다. 스냅샷 이후에 폐기한 토큰이 되살아나는 것을 막는다. 새 페어링 키를 설정하고 각 기기를 새로 연결한다. 원래 운영 코어의 기기는 영향받지 않는다.
6. 완료 작업·결과·등록 자료·요청 ID는 보존한다. 복원된 실행 상태는 기록과 다를 수 있으므로 과거 영수증을 최신 작업 상태로 해석하지 않는다. 최신 `/api/state`를 다시 조회한다.
7. 도구는 서버를 시작하지 않는다. 먼저 로컬 loopback에서 새 코어를 실행해 실제 결과와 중복 요청을 확인한다. 운영 호스트에 올리는 전환은 별도 단계다. 기존 Koyeb 컨테이너 guard/볼륨 조건을 우회하지 않는다.

독립 위치에 암호화 파일을 보관하고 그 사본으로 복원해야 독립 백업 검사다. 같은 Koyeb 볼륨의 `.bak`, API 상태 화면 저장, 정상 재배포 보존은 이를 대체하지 않는다. 백업 파일 하나의 성공으로 정기 백업·보존 기간·최근 데이터 손실 한도·운영 복구 시간을 보장하지 않는다.

## 분실 기기 차단

소유자 bearer로 `GET /api/devices`에서 ID·이름·플랫폼·등록/마지막 확인/폐기 시각만 조회한다. 원문 토큰과 해시는 반환하지 않는다. `POST /api/devices/DEVICE_ID/revoke`에 새 `requestId`를 보내 해당 기기만 차단한다. 같은 요청은 같은 영수증을 돌려준다. 이미 폐기한 기기를 다시 폐기해도 최초 시각을 유지한다.

다른 기기 토큰은 이 관리자 경로를 사용할 수 없다. 기존 앱 자신의 폐기 경로는 유지한다. 페어링 키 변경만으로 기존 기기를 폐기했다고 판단하지 않는다. 이번 추가는 관리자 API이며 폰의 기기 관리 화면은 아직 추가하지 않았다.
