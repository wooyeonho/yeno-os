# BLACKHOLE OS — Codex 실행 인계서
작성: 2026-09-25 (Asia/Seoul)
대상: 실제 프로젝트에 접근하는 Codex 구현 세션
목적: 기존 작업과 결정을 이어받아 Windows 설치부터 Android 실사용까지 완료
출처: 이 대화의 사용자 지시와 사용자가 전달한 PC 연결 세션의 보고

> 이 문서는 실행 지시와 대화 인계 자료다. 현재 PC 소스 코드·Git 저장소·비밀값을 포함한 패키지가 아니다.
> 아래 PC 상태와 구현 내역은 **사용자가 전달한 다른 실행 세션의 보고**다. 작성 세션이 해당 PC의 최신 파일을 직접 검증한 것은 아니다.
> 수신 Codex는 실제 저장소의 최신 파일·diff·실행 결과를 확인하여 상태를 갱신한다.

## 0. Codex에게 내리는 실행 지시

너는 이번 작업의 구현·통합·빌드·검증 담당이다. 이 문서를 읽고 실제 저장소를 확인한 뒤 작업을 시작하라. 기존 결정을 반복해서 묻거나, 요구사항 문서를 새로 쓰고 다음 지시를 기다리는 것으로 종료하지 않는다.

목표는 다음 사용 흐름이다.

**Android BLACKHOLE 앱에서 작업을 요청 → 같은 Windows resident-v2가 접수·실행 → 진행과 결과가 앱에 표시 → 앱을 다시 열거나 코어를 재시작해도 요청과 결과가 보존된다.**

연호님이 PowerShell에 명령이나 페어링 키를 입력해야 하는 설치 흐름을 해소한다. 필요한 소유자 로그인·기기 확인은 코드와 준비를 끝낸 뒤 최소한의 구체적인 조작으로 안내한다. 실행 권한은 실제 도구의 허용 범위로 판단한다.

기존 BLACKHOLE의 Homunculus·Jarvis·Kirby·Shadow Army·Verifier/JEV·기억·로컬 모델을 이어서 사용한다. 이번 설치·연결 완료를 전체 OS의 모든 장기 기능이 완성됐다는 뜻으로 확대하지 않는다. 기존 미완료 기능은 정본 기록의 목록과 연결하여 누락 없이 남긴다.

### 반드시 구분할 능력

1. 실제 PC 폴더를 읽고 수정할 수 있는가.
2. 실제 Windows에서 PowerShell/Node/빌드 도구를 실행할 수 있는가.
3. 실제 PC의 브라우저·앱을 조작할 수 있는가.
4. 실제 Android 기기를 조작하거나 화면을 확인할 수 있는가.
5. 해당 소스 버전으로 Windows/Android CI를 실행할 수 있는가.

FUSE 파일 접근과 Windows 프로세스 실행은 별개다. Linux 셸이 Windows 폴더를 본다는 이유로 Windows에서 명령이 실행된다고 가정하지 않는다. 다른 세션의 도구 제한이나 연결 상태를 현재 세션의 사실로 재사용하지 않는다.

이 대화의 작성 세션에는 Windows 실행·PC 조작 경로가 확인되지 않았다. 이 사실은 다른 PC 연결 세션의 FUSE 연결이 가짜라는 근거가 아니다.

### 코드 자체를 빠짐없이 이어받기

우선 실제 PC의 같은 작업 폴더를 Codex 프로젝트로 연다. git status, staged/unstaged diff, untracked 파일, git log를 확인한다.

마지막 보고에는 다음 두 문장이 함께 있었다.
- “작업 트리를 그대로 두고 커밋하지 않았다.”
- 신규 설치 파일을 “저장소에 커밋해 뒀다.”

서로 충돌하므로 실제 Git 기록으로 판정한다. 파일이 폴더에 있다는 것과 커밋에 포함됐다는 것을 구분한다.

실제 폴더 연결을 사용할 수 없어 소스를 옮겨야 한다면, 기존 연결 세션이 다음을 준비한다.
- 기준 전체 SHA와 브랜치, 현재 상태 목록.
- 해당 로컬 브랜치의 필요한 커밋을 포함한 Git bundle 또는 검토된 소스 스냅샷.
- tracked 파일의 미커밋 변경을 보존한 binary patch 또는 스냅샷 반영분.
- 신규 installer 등 검토된 untracked 소스 파일.
- 파일 목록과 SHA-256, 적용 순서.

Git bundle만으로 미커밋·untracked 변경은 전달되지 않는다. 인증파일·토큰·.env·개인 런타임 데이터·기기 보관소는 소스 인계에서 제외한다. 원격 main이나 오래된 scratch 사본을 현재 PC 코드 대신 사용하지 않는다. 누락된 현재 소스가 필요한 작업만 정확히 차단 상태로 표시한다.

## 3. 지금까지 진행된 내용 — 재검증할 인계 사실

### A. 구조 확인 보고

- runtime/resident.mjs가 runtime/server.mjs의 start()를 호출하므로 실제 HTTP 라우트는 server.mjs에 있다.
- controller가 사용하는 devices/enroll, state, commands, control, world, drives/status, artifacts/:id, projects/:id/milestones 및 관련 studio/production/hankki 경로의 구조적 호환이 보고됐다.
- Bearer 인증, requestId 기반 접수·중복 방지·receipt 복구 구조가 있는 것으로 보고됐다.
- runtime/test/phone-acceptance.test.mjs의 이전 합성 흐름은 resident-v2 실사용 증거가 아니다.
- Self-Review Gate라는 이름의 기존 장치는 검색에서 확인되지 않았다는 보고가 있다. 있다고 가정하거나 그 이름 때문에 구현을 중단하지 않는다.

이들은 코드 검토·과거 시험에 대한 보고다. 실제 최신 바이너리와 8790 코어의 성공을 의미하지 않는다.

### B. Windows resident 설치 스크립트 검토 보고

기존 검토에서는 다음 범위로 확인됐다고 한다.
- 소유자 계정의 예약 작업 하나.
- RunLevel Limited, LogonType Interactive, MultipleInstances IgnoreNew.
- 방화벽·Windows 서비스·레지스트리 변경 없음.
- 제거는 해당 설치가 소유한 작업만 제거하고 데이터와 키를 보존.

현재 수정된 파일에서 다시 확인한다. 기존 설치·데이터가 있으면 신규 저장소 초기화 옵션을 무조건 적용하지 않는다. 재설치는 기존 키와 데이터, 설치 소유권을 보존해야 한다.

## 4. 반복하지 않을 실패

- 현재 실제 저장소 확인 없이 폴더 이름이나 오래된 사본을 기준으로 작업하기.
- GitHub에 브랜치가 없다는 이유로 실제 PC의 로컬 브랜치를 부정하기.
- 클라우드 업로드함의 .cmd를 PC에 이미 설치된 파일처럼 안내하기.
- PowerShell에 입력할 수 없는 상황에서 같은 수동 실행 명령을 반복하기.
- 자동 키 생성만 적용하고 휴대폰이 그 키를 어떻게 안전하게 대체·전달받는지 미완성으로 남기기.
- health 응답이나 합성 테스트 통과를 실제 휴대폰 작업 완료로 보고하기.
- “코딩은 다른 AI의 역할”이라는 이유로 구현을 하지 않고 기록만 추가하기.
- 코드 생성·빌드 성공·PR 생성에서 전체 작업 완료로 종료하기.
- 플랫폼이 금지한 실행을 .cmd·바로가기·자동실행 파일 등 다른 경로로 우회하기.

제품용 설치 파일을 만드는 것과 현재 세션이 그 파일을 실행할 권한은 별개다. 정식으로 허용된 실행 도구가 있으면 사용한다. 클릭 실행은 도구 정책이 해당 설치 실행을 허용할 때만 이용한다. 도구 제한을 없애기 위한 방법으로 사용하지 않는다.

## 5. 이어서 실행할 작업 순서

### 1단계 — 현재 상태와 실제 완료 시나리오 고정

- 실제 경로, remote, branch, 전체 SHA, 변경 목록, 실행 도구 범위를 기록한다.
- AGENTS.md와 그 지침이 요구하는 문서, 실행 상태 파일 최신 절, 관련 설치·서버·controller·CI 코드를 읽는다.
- 기존 설치 작업, 실행 중 인스턴스, 포트, 데이터 디렉터리, Node·빌드 의존성, Tailscale·Ollama의 실제 상태를 가능한 범위에서 확인한다.
- 아래 완료표에 사용할 **정확한 앱 입력 문장 또는 API payload**, 기대 결과, timeout, 검증 환경을 먼저 적는다. 기존에 지원하는 무해한 문서/파일 생성 작업을 우선 선택한다.
- “현재 사용자 자료를 파괴하지 않는 가역적인 시험” 범위를 정하고 작업을 계속한다.

### 2단계 — 설치 자동 생성 경로를 실제로 완성

- 보고된 최신 변경을 diff에서 확인하고 기존 코드와 중복 구현하지 않는다.
- CSPRNG 생성·인코딩·키 길이·저장·파일 권한·오류 처리가 Windows PowerShell 5.1에서 동작하는지 검증한다.
- 신규 설치, 재설치, 중간 실패 후 재시도에서 키·데이터가 무단 교체되거나 다른 설치를 덮어쓰지 않는지 확인한다.
- stdout/stderr, 예외, CI 로그, 테스트 보고서가 키를 노출하지 않게 한다.
- launcher의 상대 경로, 공백·한글 경로, 종료 코드, 의존성 누락 안내를 확인한다.
- 설치와 실제 상태 확인을 연결한다. 파일 생성이나 작업 등록 성공만으로 실행 성공을 표시하지 않는다.

### 3단계 — 키를 직접 옮기지 않는 페어링 완성

기존 기기 등록·철회 계약을 재사용하고 서버·Windows 소유자 UI·Android 입력 경로를 함께 만든다.

최소 보안·동작 계약:
- 초대 발급은 인증된 소유자의 명시적 동작으로 시작한다.
- 앱이 사용할 주소는 실제 선택된 코어의 사설 HTTPS 주소다.
- QR 등을 사용한다면 장기 owner 키 대신 만료·단일 사용·기기 등록 전용의 별도 초대값을 사용한다.
- 미인증 사용자가 QR이나 등록 초대를 발급·조회할 수 없게 한다.
- 초대의 잘못된 값, 만료, 재사용, 중복 요청, 취소, 재시작의 의미를 명확히 정하고 검증한다.
- Android는 실제 스캔/확인/등록 UI와 기기별 인증정보의 기존 안전한 저장소 연결까지 구현한다.
- 기존 기기 보관소의 소유자 암호·잠금 해제 과정이 있다면 보호 수준을 유지한다. 필요한 소유자 입력은 앱의 적절한 화면에서 받으며 채팅이나 터미널로 옮기지 않는다.
- 기존 휴대폰의 연결 정보와 이전 요청을 임의로 삭제하지 않는다. 코어 전환이 필요한 경우 대상과 영향을 분명하게 표시한다.
- 기기 철회 후 옛 인증정보가 거부되고 새 등록으로 복구되는지 확인한다.
- 비밀값과 유효한 초대 QR을 공개 보고서·스크린샷·CI 산출물에 포함하지 않는다.
- Tailscale이 설치되지 않았어도 초대 계약·UI·만료·재사용·오류 경로 구현과 자동 검증은 먼저 진행할 수 있다.

QR 표시만으로 완료 처리하지 않는다. 소유자 UI가 초대값을 안전하게 발급받는 인증 경로와 Android가 이를 소비하는 경로까지 검증한다. 같은 사설망이라는 이유만으로 인증을 생략하지 않는다.

구현 방식은 현재 코드에 맞춰 최소 변경으로 정한다. Tailscale 계정 신원 등을 새 인증 근거로 도입해야 한다면 기존 인증 설계 변경으로 명시하고 필요한 결정을 받는다.

### 4단계 — 실제 코어·설정·로컬 모델 연결 확인

- controller가 선택한 코어가 resident-v2/8790인지 실제 응답으로 확인한다.
- 8792 설정 화면이 같은 resident의 올바른 설정을 읽고 저장하는지 확인한다.
- Ollama loopback 설정, 선택 모델, 저장 후 재시작 보존을 확인한다.
- 설치 성공과 실제 모델 호출 성공을 따로 증명한다. 기존 허용 범위의 로컬 모델로 작은 작업 하나를 실행하고 provider/model·요청·결과의 실제 연결을 남긴다.
- 로컬 모델이 준비되지 않았으면 정확한 구성 문제를 표시한다. 유료 모델이나 공개 네트워크 모델로 조용히 대체하지 않는다.

### 5단계 — 빌드와 배포 가능한 파일

- 현재 저장소의 실제 빌드 명령, lockfile, 런타임 버전 요구사항, 기존 CI를 따른다.
- Windows PowerShell 파서·실행 시험은 실제 Windows 또는 해당 변경을 포함한 Windows CI에서 실행한다.
- Android 빌드를 실행해 설치 가능한 APK를 확보한다. 프론트엔드 bundle은 APK가 아니다.
- 기존 Tauri Windows 빌드 대상과 실제 실행물/설치물을 확보한다. controller EXE만 만들어 놓고 resident 설치까지 포함됐다고 보고하지 않는다.
- Windows 설치 진입점, 필요한 runtime 파일·의존성, controller 산출물의 관계를 실제 실행으로 확인한다.
- 결과물마다 경로, 크기, SHA-256, 빌드 로그, 도구 버전, 소스 기준을 기록한다.
- 빌드가 미커밋 변경을 포함하면 HEAD만으로 출처를 설명하지 않는다. 전체 HEAD + diff/신규 파일의 식별 정보로 해당 빌드의 소스를 고정한다.
- local 변경, 허용된 빌드, 관련 테스트는 계속 진행한다. 원격 push·배포·merge는 해당 작업에 이미 주어진 허용 범위에 맞춰 판단한다.

### 6단계 — 실제 Windows 실행과 휴대폰 인수

- 정식으로 허용된 Windows 실행 경로에서 설치를 실행한다.
- 신규/격리 시험과 기존 사용 중 설치를 구분한다. 실제 사용자 데이터와 현재 작업을 보호한다.
- authenticated readiness, 소유권이 맞는 예약 작업, 실행 중 인스턴스와 포트를 함께 확인한다.
- Tailscale의 기존 설치·로그인을 먼저 확인한다. 필요한 소유자 로그인은 코드·빌드·허용된 시험을 마친 뒤 구체적인 조작으로 요청한다. 비밀값을 채팅으로 받지 않는다.
- PC에서 사설 HTTPS가 되는 것과 실제 휴대폰 연결을 구분한다.
- 아래 완료 시나리오를 끝까지 실행한다. 중요한 수정 후에는 이미 통과한 흐름을 포함해 다시 확인한다.
- 실제 휴대폰 도구가 없다면 실행 가능한 산출물을 준비하고 짧은 소유자 확인 절차를 제공한다. 소유자가 알려준 결과는 소유자 확인이라고 기록한다.

## 7. 상태 표기

| 상태 | 의미 |
|---|---|
| CONFIGURED | 소스·설정을 준비했으나 해당 동작을 아직 실행하지 않음 |
| ARTIFACT CREATED | 특정 파일·APK·실행물이 실제 생성됨. 동작 검증은 별도 |
| RAN | 명령·시험·앱을 실행했으며 실행 근거가 있음 |
| RAN-UNVERIFIED | 실행은 했으나 목표 동작 또는 필요한 실제 기기 결과가 확인되지 않음 |
| VERIFIED | 특정 시나리오가 명시된 환경에서 관찰·검증됨 |
| DEPLOYED | 특정 대상에 배포/설치 반영 근거가 있음. 전체 기능 검증을 자동 의미하지 않음 |
| BLOCKED | 외부 의존성·권한·도구·자료 때문에 특정 작업을 진행할 수 없음 |

각 상태에는 대상 기능/시험 ID, 소스 기준, 환경, 실행 시각, 명령 또는 UI 동작, 실제 결과를 붙인다. 상태는 프로젝트 전체에 하나만 붙이지 않는다.

예:
- P03 VERIFIED — 로컬 통합 시험의 만료·재사용 거부.
- P02 RAN-UNVERIFIED — APK 실행은 했지만 실제 Android 페어링 미확인.
- W01 CONFIGURED — 스크립트와 테스트 소스만 변경하고 Windows 실행 안 함.

## 8. 자율 진행과 승인·실패 관리

- 현재 목표 안의 가역적인 코드 변경, 필요한 의존성 구성, 로컬 시험, 빌드, 수정은 계속 진행한다.
- 기존 데이터·사용자 변경을 보존한다. 실제 diff를 검토하고 새 작업을 기존 미커밋 변경과 섞어 임의로 정리하지 않는다.
- 새 과금·결제, 외부 발송, 운영 배포, 기존 자격증명 교체, 작업 폴더 밖 삭제 등은 기존에 주어진 구체적인 허용 범위를 확인한다. 부족하면 검토 가능한 결과를 준비한 뒤 필요한 결정만 묻는다.
- 신규 설치의 자동 키 생성과 기존 키 교체를 구분한다.
- 이 대화에는 이번 작업의 확정된 숫자 비용·총시간 예산이 없다. 사용자의 일반 월 예산을 이 작업의 과금 승인으로 간주하지 않는다.
- 유료 실행이 새로 필요할 때는 비용과 범위를 제시한다. 이미 허용된 CI와 로컬 작업의 범위를 활용한다.
- 반복 오류는 가설·관찰·수정·결과로 기록한다. 같은 가설에서 3회 실패하면 접근법을 바꾼다.
- 기본 작업 규칙으로 단일 차단 문제에 대해 서로 다른 3개 가설 또는 45분을 소진하면 그 항목을 기록하고 다른 독립 작업을 진행한다. 이 수치는 사용자 승인 예산이 아니라 무의미한 반복을 막기 위한 기본 운영값이며 필요하면 근거와 함께 조정한다.
- 병렬 에이전트를 쓰면 먼저 서버/클라이언트/설치의 요청·응답·인증·오류 계약을 정한다. 최종 통합과 완료표 검증은 수신 Codex가 책임진다.
- 진행 보고는 완료한 것, 다음 작업, 현재 차단 여부를 짧게 알린다. 보고 직후 계속할 수 있으면 작업을 이어간다.
- 세션 종료나 컨텍스트 한계 전에 정본 파일에 재개 정보를 남긴다. 기록 파일이 실행을 계속하는 백그라운드 프로세스라고 주장하지 않는다.

실행 도구가 제한된 경우:
1. 제한된 항목과 근거를 정확히 기록한다.
2. 허용된 구현·빌드·자동 검증을 완료한다.
3. PC 실행이 가능한 정식 환경이나 최소한의 소유자 동작이 필요한 지점을 한 번에 전달한다.
4. 같은 PowerShell 입력 요청을 반복하거나 제한을 우회하지 않는다.

Obsidian은 이번 인계 대상 코드 저장소와 별개다. 별도 요청 없이 Vault를 수정하지 않는다. 이후 별도 Vault 작업 시 원문 보호·초안 위치·승인·변경 기록 규칙을 따른다.

2. 설치·사용할 파일과 정확한 위치.
3. 직접 확인한 완료표와 남은 확인.
4. 소유자 동작이 필요하면 가장 적은 구체적인 조작.
5. 재개 지점.

계획·코드·테스트·빌드만 통과한 경우는 그 범위대로 보고한다. 설치와 휴대폰 실제 요청·결과가 남아 있으면 “실사용 완료”라고 쓰지 않는다.

## 10. 즉시 착수 메시지

이 문서를 실행 인계서로 삼아 실제 PC의 yeno-os 저장소와 최신 미커밋 변경부터 확인하고, 기존 상태를 이어받아 구현·빌드·Windows 실행·Android 페어링·실제 요청/결과·재시작 복구까지 수행하라. 정해진 결정은 재사용하고, 허용된 일은 계속 진행하라. 코드 전달이나 도구 연결이 부족하면 해당 경계를 정확히 밝히고, 가능한 독립 작업을 먼저 끝내라. 완료표의 근거가 갖춰질 때까지 요구사항 요약만 남기고 종료하지 마라.
