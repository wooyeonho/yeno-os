# BLACKHOLE OS 제품 비전

## 목적
BLACKHOLE OS는 사용자가 휴대폰에서 목표나 작업을 말하면, Android 앱과 연결된 Windows PC의 AI가 조사·계획·실행·검증하고 진행 상황과 결과를 돌려주는 개인 AI 운영체제다. 결과를 기억하고 재사용해 사용자의 시간과 비용을 아끼고, 수입·브랜드·성과를 키우는 데 도움을 준다. 결과를 보장한다고 주장하지 않고 실제 근거와 성과로 판단한다.

## 핵심 작업 흐름
요청과 맥락 파악 → 목표·우선순위 설정 → 계획 → 필요한 작업자에게 분배 → 실행 → 독립 검증 → 결과와 실패 기록 → 기억에 저장 → 다음 행동 결정.

각 단계의 상태는 실제 상태와 일치해야 한다. 실행하지 않았거나 확인하지 않은 일을 완료로 표시하지 않는다.

## 구성 요소의 의도
- Jarvis: 사용자와 대화하고 전체 작업을 조율한다.
- Kirby: 파일·자료·작업 결과를 정리해 기억하고 재사용한다.
- Homunculus / Seven Drives: 사용자의 목표와 우선순위를 반영한다. 정의는 저장소의 기존 기준을 읽고 따른다.
- Shadow Army: 조사·제작 등 작업을 나눠 수행한다.
- Verifier / JEV: 결과를 독립적으로 확인하고 판단 근거를 기록한다.
- Android 앱: 요청·승인·진행·결과를 보여준다.
- Windows resident: 허가된 작업을 PC에서 실행하고 상태를 보고한다.

## 필수 원칙
- 기존 코드와 결정을 먼저 확인하고 재사용한다.
- 보안은 소유자 인증, 기기별 등록·폐기, 최소 권한, 감사 기록을 기본으로 한다. 비밀값은 화면·로그·채팅에 노출하지 않는다.
- 파일의 위험한 삭제, 외부 발송, 결제, 자격증명 교체, 운영 배포는 실행 전에 승인을 받는다.
- 실패와 한계를 숨기지 않는다. 같은 원인 가설로 세 번 실패하면 접근법을 바꾸고 기록한다.
- 장기 비전 전체를 한 번에 새로 만들지 않는다. 각 단계는 실제 작동과 검증을 마친 뒤 확장한다.

## 우선 구현 순서
1. Android 요청 → Windows 실행 → 진행 표시 → 결과 확인.
2. 재시작 후 작업·결과 복구, 오프라인·실패 표시, 안전한 페어링.
3. 기반 흐름이 검증된 뒤 Shadow Army, JEV, 기억 재사용과 추가 기능을 기존 코드에 맞춰 확장한다.

이 문서는 장기 비전만 기록한다. 현재 브랜치·HEAD·설치 여부·테스트 결과는 정본 실행 기록에 기록한다.

## 2026-09-25 보완 — 전체 목적과 요구사항의 근거

이 절은 기존 본문을 보존하면서 소유자의 보완 지시와 실제 열람한 자료의 근거를 덧붙인다. 요구사항이 충돌하면 이번 소유자 지시가 과거 초안보다 우선한다. 구현 상태·실행 기록·테스트 결과는 `CLAUDE_EXECUTION_STATE.md`에만 기록한다.

### 사용자가 얻어야 할 결과

휴대폰 **또는 PC**에서 원하는 결과를 말하면, BLACKHOLE은 맥락과 허용된 자료를 살펴 계획하고 필요한 AI·도구로 실행한 뒤 근거를 검사해 결과를 돌려준다. 한 번의 요청에서 허가된 일을 가능한 끝까지 처리한다. 사용자가 매번 세부 절차나 터미널 명령을 대신 수행해야 하는 제품으로 만들지 않는다. 승인·기기 조작이 꼭 필요한 경계에서는 이유와 준비된 다음 행동을 명확하게 제시한다.

과정·결과·실패를 출처, 요청/임무 ID, 산출물, 검증 근거와 연결해 재사용 가능한 기억으로 남긴다. 장기 가치는 시간·비용 절감과 수입·이름·전문성·성과에 기여하는 것이다. 실제 산출물과 결과 근거로 판단하며 수익, 완전 자율성, 학습 효과를 보장하지 않는다.

### 구성 요소의 의도와 코드 확인 지점

아래 경로는 구현을 대조할 위치다. 이름·파일·함수의 존재만으로 전체 역할이 작동한다고 판정하지 않는다. 실제 구현 범위와 검증 여부는 정본 실행 기록에서 따로 관리한다.

| 구성 | 유지할 의도 | 기존 코드 확인 지점 |
|---|---|---|
| Jarvis | 대화에서 목표를 이해하고 실행 순서·전체 작업 조율 | `runtime/server.mjs`의 voice/임무 경로, `runtime/lib/shadow-army.mjs`, `runtime/lib/closed-loop.mjs` |
| Kirby | 출처 있는 자료·기억·능력·산출물을 재사용 | `runtime/lib/kirby.mjs`, `memory-recall.mjs`, `memory-embeddings.mjs`, `capabilities.mjs` |
| Homunculus / Seven Drives | 기존 목표·우선순위와 선택 이유 유지 | `runtime/lib/seven-drives.mjs`, `motivation.mjs`, `quests.mjs`; 기존 영속 ID와 의미를 임의 교체하지 않음 |
| Shadow Army | 허용된 역할별 조사·제작 및 의존 작업 실행 | `runtime/lib/shadow-army.mjs`, 서버의 job/mission 배선 |
| Verifier / JEV | 산출물 무결성·의미·막힘·대안의 근거를 별도로 검토 | `outcome-verification.mjs`, `semantic-verification.mjs`, `jev.mjs`, `jev-recovery.mjs`, `jev-recovery-verifier.mjs` |
| Android / Windows resident | 같은 요청·작업·결과를 보는 기기와 PC 실행 본체 | `apps/controller`, `runtime/resident.mjs`, `scripts/blackhole-resident.ps1` |

검증 판정은 실행 권한을 새로 만들지 않는다. 산출물 파일이 만들어진 것, 내용이 요구에 맞는 것, 실제 사업 성과가 난 것을 구분한다. 기억 검색·임베딩·XP는 모델 가중치 학습의 증거가 아니다.

### Obsidian 사용과 향후 동기화 경계

- 현재 Vault는 요구사항과 결정의 근거로 읽는다. `00_INBOX_RAW`는 수정·삭제·덮어쓰기하지 않는다.
- 정리본이 필요하면 `01_DRAFTS`에 새 초안만 만든다. 기존 노트의 링크·분류·본문 변경은 별도 승인 후에 하며 Vault 작업은 `CHANGELOG.md`에 기록한다.
- 앱과 Vault의 실제 동기화는 별도 장기 요구사항이다. 현재 연결돼 있다고 가정하거나 이 문서 작업을 제품 동기화로 부르지 않는다.
- 구현 전 기존 기억 이벤트/outbox/어댑터, 접근 허용 경로, 민감정보 제외, 변경 주체, 중복 방지, 충돌·재시작·철회·감사 이력을 대조한다. 파일 가져오기와 내보내기, 단방향 초안 작성과 양방향 원문 수정은 서로 다른 권한이다.
- 첫 동기화 후보는 소유자가 허용한 자료의 읽기와 `01_DRAFTS` 새 초안 생성이다. 원문 덮어쓰기, 삭제 전파, 외부 업로드, 전체 Vault 자동 수집을 기본값으로 두지 않는다. 출처와 신뢰 등급을 유지한다.

### 단계별 확장 원칙

1. **현재 우선 수락:** Android 요청 → 같은 Windows resident 실행 → 진행·결과 확인, 앱/코어 재시작, PC 오프라인·실패, 안전한 기기 등록·철회를 실제로 검증한다. 브라우저 대체 시험과 APK·실기기 시험을 구분한다.
2. **위 흐름 수락 후:** 같은 요청의 자료·기억 출처, 계획·역할별 실행, 독립 검증, 결과·실패 기록을 하나의 추적 가능한 임무로 연결한다. 이미 있는 기능을 중복 작성하지 않는다.
3. **그 다음:** 소유자 실제 과제에서 시간·비용·수정 횟수·결과 품질을 측정하고, 승인된 Obsidian 초안 교환과 재사용을 좁은 범위부터 검증한다.
4. **장기:** 개선 후보의 비교 평가·채택·복원을 단계화한다. 실제 학습/QPU 등 과거 문서의 확장 요구는 삭제하지 않되, 장비·비용·권한·유용성 증거를 별도로 요구한다. 이번 휴대폰 흐름의 완료 조건을 대체하거나 먼저 확장하는 근거로 쓰지 않는다.
