# BLACKHOLE 재설계안 — 오픈소스 엔진 위에 우리 개념을 녹인다 (2026-09-30, Claude 작성)

**성격: 설계 초안.** 개념·엔진 수준의 설계이며, 모듈 단위 대응(유지/어댑터/교체)은 Codex가 코드를 읽는 감사(AUD-1)와 `BLACKHOLE_TARGET_ARCHITECTURE.md`(AUD-4)에서 확정한다. 후보의 관측값은 `OSS_CANDIDATE_MAP_20260930.md` 참조. 오픈소스의 동작 설명은 각 프로젝트의 공개된 일반 설계에 대한 Claude의 이해이며, 채택 전에 Codex가 실제로 기동해 확인한다.

## 0. 원칙

1. **엔진은 빌려 오고, 개념은 얹는다.** 오픈소스는 기억·계획·실행·로그·음성 같은 엔진을 준다. 칠죄종·그림자군단·커비·JEV·양자·자비스는 그 엔진 위에서 "무엇을 원하고, 무엇을 인정하고, 무엇이 등급을 올리는가"를 정하는 정책층이다.
2. **전면 재작성 금지(strangler).** 지금 있는 126개 lib 모듈과 1,398개 이상의 시험은 안전망이다. 한 번에 한 모듈을 어댑터 뒤에서 갈아 끼우고, 폴백을 유지하고, 깨지면 고쳐서 통과시킨다(지시서 2.1절).
3. **외부 출력은 전부 막(membrane)을 통과한다.** `oss:<이름>@<sha>` 표식 + `unverified`로 들어와 기존 `outcome-verification`/`semantic-verification`을 거친 뒤에만 점수·등급·배부름에 쓰인다. 모델도 오픈소스도 권위가 아니다.

## 1. 새 구조 (3층)

```
[3층 정책층 + 화면 — 우리 것]
  칠죄종 정의·문턱 · 증거 인정 기준 · 그림자 소환/등급 정책 · 커비 카피 규칙 · JEV 판정 기준 · 양자 결정 규칙 · 소유자 승인 · JARVIS 화면
        ▲ 설정·규칙으로 얹힘                        ▼ 결과는 여기서 검증
[2층 막·어댑터층 — 우리 것(얇게)]
  표식 oss:이름@sha · unverified 기본 · 비밀값/파일 경계 · 타임아웃·자원 제한 · 요청 원장 · 커넥터 영수증 · 실패는 not_ok로(가짜 성공 금지)
        ▲ 어댑터 인터페이스                          ▼ 호출
[1층 오픈소스 벽돌층 — 가져온 것(A 복사·개량 / B 별도 프로세스)]
  다중 에이전트 실행 · 기억 · 모델 라우팅 · 브라우저 · 검색 · 음성 · 내구 실행 · 증명 형식 · 양자 시뮬레이터 · 상태 오브
```

## 2. 개념별 융합 설계

각 항목: **빌려 오는 엔진(후보, 가설) → 우리가 얹는 것 → 지금 모듈(가설적 대응)**.

### 2.1 칠죄종 호문쿨루스 (욕망)
- 엔진: generative_agents의 "기억 스트림 → 성찰 → 계획" 구조(최근성·중요도·관련성으로 기억을 꺼내고, 주기적으로 성찰해 상위 통찰을 만든다). 루프 실행기는 LangGraph 같은 상태 그래프 후보.
- 얹는 것: 각 죄는 성찰의 **관점**이다. 배고픔은 실제 기록(결과 원장, 측정 공백, 미검토 초안)에서만 계산하고, 배부름은 검증된 결과로만 온다(욕망 v3 그대로). 성찰이 낸 통찰은 `cue`(단서)일 뿐 점수·확률이 아니다. 대가는 정직하게 남긴다.
- 모듈: `seven-drives`, `drive-state`, `drive-outcomes`, `motivation`, `lust-mirror` — 정책은 유지, 기억 조회·성찰 루프는 엔진 교체 후보(`memory-*`와 중복 확인).

### 2.2 그림자군단 (손발)
- 엔진: 역할 기반 다중 에이전트 실행(LangGraph, CrewAI), 코딩 실행기(OpenHands). 중단 후 승인(휴먼 인 더 루프) 흐름은 소유자 승인 경로와 맞는다.
- 얹는 것: 그림자 = 지금처럼 **내구 작업 기록 하나**(자체 잡 엔진을 새로 만들지 않는 기존 설계 유지). 실행은 OSS 러너에게 맡기되 출력은 unverified로 돌아오고, 등급·XP는 동결된 `solo-leveling.mjs` 계약이 검증된 증거로만 올린다. "일어나라(arise)"는 검증된 가치 있는 승리에서만.
- 모듈: `shadow-army`, `shadow-roster`, `shadow-profiles`, `shadow-arise-state`, `agent-engine`, `persistent-bots` — 러너 층이 어댑터 후보, 기록·등급은 유지.

### 2.3 커비 (흡수·카피)
- 엔진: Voyager의 스킬 라이브러리(검증된 능력을 설명과 함께 저장하고 필요할 때 꺼내 조합) 패턴, MCP 서버를 "삼킬 수 있는 능력"으로. 코드 자체는 오래되어(2024-04) 설계 참조.
- 얹는 것: 흡수 = A/B/C 등급 규칙(복사·개량/별도 프로세스/제외)과 독립 근거 검증기. 활성 능력마다 이름·출처 해시·모자(`copyAbility`), 조합(믹스)은 실제 조합 증거가 있을 때만. 흡수 후보는 gap-scout이 찾고 소유자 승인 전까지 비활성 초안.
- 모듈: `kirby`, `kirby-copy`, `absorb-inbox`, `gap-scout`, `capability-*`, `repository-evidence` — 유지, 흡수 실행 경로는 OSS-first 규칙으로 정렬.

### 2.4 JEV (판례를 쌓는 판사)
- 엔진: 보정·불확실성 계열(MAPIE의 conformal prediction: 미리 정한 오류율 안에서 예측 집합을 주고 애매하면 기권 쪽으로). 현재 Wilson 하한은 JS 그대로 유지.
- 얹는 것: 유형 있는 판정, `decided|uncertain|abstain|blocked`, dissent(스케줄러와 다른 판단) 기록, `authorizesDispatch:false` 불변. 기권 문턱을 손으로 정한 값 대신 보정 근거에서 나오게 할 수 있는지는 감사에서 검토(Python 의존은 별도 프로세스 또는 개념만 JS로 이식).
- 모듈: `jev`, `jev-calibration`, `jev-docket*`, `jev-recovery*` — 판정 기준은 우리 것, 보정 계산만 교체 후보.

### 2.5 양자
- 엔진: 현행 `quantum-circuit`(이미 사용) 유지. Qiskit/PennyLane은 실제 QPU 연결이 필요해질 때만.
- 얹는 것: 중첩(관측 전 후보 상태)→측정(관측 시 붕괴) 규칙과 "시뮬레이터라는 사실 그대로" 표기.
- 모듈: `quantum-decision*`, `quantum-statevector`, 동결 `recovery-one-of-qpu` — 변경 최소.

### 2.6 자비스 (목소리·얼굴)
- 엔진: 실시간 음성 대화(pipecat, LiveKit agents), 로컬 음성 인식(faster-whisper), 오브 화면(thinking-orbs 이미 적용). 로컬 모델(Ollama) 우선 조건 유지.
- 얹는 것: 오브 상태는 저장된 기록에서만, 음성 응답은 7죄 목소리·JARVIS 레지스터. 모델 제공자는 복합(Gemini·GPT·NVIDIA·Ollama)이며 로컬만으로 시험하다 막히면 안 된다.
- 모듈: `gemini-live`, `live-ws`, `jarvis-settings`, 화면의 `jarvis-orb.mjs`/`jarvis-scene-model.mjs`.

### 2.7 영수증·증거 (블랙홀의 핵심)
- 엔진: 증명 형식(in-toto류 증명 구조 — 라이선스 확인 전 보류, 투명 로그 체크포인트 형식 참조: rekor/tessera).
- 얹는 것: "모든 주장에 영수증" — TYPE_AUTHORITY(모델은 권위가 아님), 출처 종류, 해시 체인, 공개 영수증 페이지(S14)·제3자 증명(S15). 서버를 붙이기보다 **형식을 따라** 나중에 외부 검증이 가능하게.
- 모듈: `mission-receipts`, `receipt-attestation`, `l5-chain`, `outcome-verification`, `outcome-reality`.

### 2.8 복구·내구 실행
- 엔진 후보: DBOS(PostgreSQL 필요), Temporal(별도 서버). 로컬 우선·오프라인 조건과 충돌 가능성이 커서 **가장 마지막**에 검토. 동결 `recovery-one-of-qpu.mjs`는 불변.

### 2.9 기억·모델·브라우저·검색 (흔한 기능)
- 기억: mem0 등과 현행(Obsidian 정본 + Supabase 어댑터 + `memory-*`) 중복 확인. Obsidian 정본 원장은 유지.
- 모델 라우팅: LiteLLM은 LICENSE 확인 후. 브라우저: browser-use 등. 검색: SearXNG(AGPL — 별도 프로세스로 띄워도 라이선스 의무가 자동 해결되지는 않으므로 수정·네트워크 제공 여부를 확인, 법률 자문 아님) 또는 기존 G1 게이트웨이.

## 3. 불변식 (재설계해도 절대 안 바뀜)

`authorizesDispatch:false`(JEV·양자·게이트 전부) · 소유자 최종 승인(실제 코드에 붙이는 순간) · 동결 3파일 해시 · 자격증명 소유자 전용 · `00_INBOX_RAW` 읽기전용 · 근거 없는 등급·확률·비용 조작 금지 · 실패를 성공으로 포장 금지 · 오픈소스 출력은 unverified로 시작.

## 4. 교체 순서 제안 (가설 — 감사 결과로 조정)

효과 큼 × 위험 작음 × 분리 쉬움 순:
1. 음성 인식(faster-whisper, 별도 프로세스) — 격리돼 있고 기존 시험 영향은 작다. **그러나 Codex 지적: 공식 CPU 벤치마크상 small int8도 약 1.5GB RAM이라 이 PC에서 가볍다고 확정할 수 없다. 여유 메모리 실측 전에는 순서 1번 자리도 확정 아님(더 작은 모델·다른 후보·클라우드 폴백 포함 검토).**
2. 검색(SearXNG B 전용 또는 G1 게이트웨이 뒤) — 이미 게이트웨이 경계 존재.
3. 브라우저 조작(`browser-*`) — 어댑터 경계가 이미 분리돼 있어 보임(감사에서 확인).
4. 모델 라우팅(LiteLLM, 라이선스 확인 후).
5. 그림자 실행 러너(LangGraph/OpenHands 어댑터).
6. 기억 중복 정리.
7. 영수증 증명 형식 채택(S14/S15와 묶음).
8. 내구 실행(마지막, 동결과 충돌 없는지 확인).

## 5. 계속 직접 만드는 것 (정책층)

무엇을 증거로 인정하나 · 칠죄종 정의와 문턱 · 그림자 등급·소환 정책 · 커비 카피 규칙 · JEV 판정 기준 · 양자 결정 규칙 · 소유자 승인 조건 · 개념 원문의 강도 · JARVIS 화면 품질 기준("세계 1위처럼 보여야 한다").

## 6. 소유자 결정이 필요한 것

- 파이썬/도커 같은 별도 실행 환경을 이 PC에 설치해도 되는지(B 등급 처음 켜기 전).
- 로컬 우선·오프라인 조건과 PostgreSQL 의존(DBOS)이 충돌할 때의 우선순위.
- 체크포인트 커밋(교체 작업 전 권장 — 미커밋 파일이 많다).

## 7. 확인하지 못한 것

- 모듈별 실제 대체 가능성(코드를 읽지 않음), 후보들의 최신 커밋 날짜, litellm·in-toto 라이선스.
- 위 "엔진 설명"은 공개 설계에 대한 일반적 이해이며 실제 기동 확인 전에는 가설이다.
